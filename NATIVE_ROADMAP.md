# План: справжня нативна компіляція NyxilumLang (x86, без VM під час виконання)

Мета Sviatoslav'а (14.09.2026): після того, як NyxilumLang зможе
компілюватись у СПРАВЖНІЙ машинний код (не в байткод для VM, яка сама
потребує повноцінної ОС/.NET під собою) — переписати ядро NyxOS (чи
його частини) цією ж мовою, а згодом і написати власний BIOS.

**Чесно про масштаб:** це НЕ "додати ще одну команду `nx build --native`"
— це фактично НОВИЙ компілятор-бекенд, порівнянний за обсягом роботи з
усім NyxOS. Причина: `VirtualMachine.cs` (1440 рядків) покладається на
CLR буквально в усьому — значення (`object`, боксовані double/string/
структури), змінні (`Dictionary<int, object>` на кадр, НЕ реальні
слоти стека), виклики функцій (керовані `Stack<>`, MaxCallDepth=10000,
НЕ справжній `call`/`ret`), замикання (CLR-делегати/мапи), винятки
(`throw`/`try` самого C#), збирання сміття (сама CLR). Нативний
компілятор мусить переізобрести КОЖНУ з цих речей руками на голому x86
— саме тому обрано найважчий, "справжній" шлях (за явним вибором
Sviatoslav'а, а не легший байткод-у-VM-в-ядрі варіант).

**Стратегія:** будувати native-бекенд ОКРЕМО від NyxOS, спершу під
ЗВИЧАЙНУ Linux (де є gdb, можна порівняти вивід з VM напряму) — і лише
ПІСЛЯ того, як він стабільно працює на нормальній ОС, переносити на
freestanding NyxOS. Змішувати "чи взагалі генерується правильний x86" і
"чи працює це без ОС під собою" одночасно — рецепт заплутатись і не
відрізнити один клас багів від іншого.

## Фаза N1 — Найменший можливий реальний зріз (доказ, що ідея працює) ✅ ЗАВЕРШЕНО (14.09.2026)

команда `nx compile-native <file.nx> [-o out]`): цілі числа, `+ - * / %`,
`var`, `print()` - СПРАВЖНІЙ 32-бітний статично злінкований ELF, вивід
побайтово звірено з існуючою VM. 2 реальні баги знайдено й виправлено
(print() - окремий вузол AST PrintStatement, не CallExpression).

1. **Мінімальний підмножина мови**: цілі числа, `+ - * /`, `var`,
   `print()`, ОДНА функція `main()` без параметрів. Жодних if/while/

4. **Живий тест**: скомпілювати `var a = 2 + 2 print(a)`, зібрати в
   реальний ELF, ЗАПУСТИТИ, побачити "4" в терміналі. Порівняти з
   виводом ТОГО САМОГО файлу через існуючий `nx run`.

## Фаза N3 — Значення й типи

8. **Представлення значень** ✅ ЧАСТКОВО ЗАВЕРШЕНО (14.09.2026, дробові
   числа). Замість повного tagged union/NaN-boxing (значно більший
   крок, і далі відкладений) - обрано СТАТИЧНИЙ (не рантайм) тип на
   рівні компілятора: `InferExprType()` визначає для КОЖНОГО виразу
   Number чи Bool ще на етапі компіляції, і компілятор генерує РІЗНІ
   інструкції/регістри залежно від типу (Number -> SSE2/%xmm0 -
   справжній 8-байтовий double, той самий формат, що вже дає
   Parser.cs; Bool -> %eax, як і в Фазі N1-N2). Це можливо, бо мова
   зараз не дозволяє змінній міняти тип у рантаймі динамічно так, щоб
   компілятор не міг вивести його статично - якщо це колись
   знадобиться, доведеться повертатись до повноцінного tagged union.
   Живцем перевірено: дробова арифметика (+ - * / %, останній - через
   trunc(a/b)-формулу), порівняння (ucomisd), унарний мінус, `print()`
   чисел (власний print_double - конвертує double в десятковий ASCII
   вручну, БЕЗ printf/libc) і bool (текстом "True"/"False" - РЕАЛЬНА
   розбіжність, знайдена звіркою з VM: VM друкує через C#-типове
   object.ToString(), яке дає "True", не "true"). **ВІДОМЕ,
   задокументоване обмеження**: print_double НЕ дає короткий
   round-trip запис для дробів без точного двійкового представлення
   (напр. 3.5/1.25 = 2.8 у VM, але "2.799999999999999" у native -
   потребує Grisu/Ryu-подібний алгоритм, окрема майбутня задача) - для
   рівно-двійкових дробів (3.5, 1.25, 4.75 і т.п.) збігається
   ПОБАЙТОВО. Функції поки повертають лише Number (bool-результат -
   тільки для return у main(), як код виходу). NyxOS-ціль
   (--target nyxos) і далі успішно асемблюється/лінкується з цим
   кодом (структурна перевірка), повний живий тест УСЕРЕДИНІ NyxOS
   для дробових чисел - ще не зроблено (наступний крок).
9. Рядки, масиви, структури - усі як вказівники на купу ✅ ЧАСТКОВО
   ЗАВЕРШЕНО (14.09.2026, рядки + масиви). Замість malloc/free з libc
   (як спершу пропонував цей пункт) - ВЛАСНИЙ, написаний ВРУЧНУ
   bump-розподілювач (`heap_alloc`, EmitHeapAllocHelper) через syscall
   brk (#45) - рішення змінено НА КРАЩЕ під час реалізації: компілятор
   і так свідомо НІДЕ не лінкується з libc (сирі syscall'и всюди,
   ближче до freestanding NyxOS), тож підключати libc ЛИШЕ заради
   malloc означало б тягнути динамічний лінкер (PLT/GOT, interpreter
   path) - значно складніша, окрема ІНЖЕНЕРНА тема, ніж написати
   40-рядковий bump-аллокатор самому. Немає free()/GC - пам'ять
   "тече", чесно, як і планувалось тут же нижче.

   **Рядки** (`ValType.String`, вказівник-eax): статичні .rodata-
   літерали, присвоєння/перевизначення змінній, print() (з рантайм
   strlen для Linux - довжина більше НЕ завжди відома на етапі
   компіляції, бо змінна могла вказувати на РІЗНІ рядки). Стара
   спецгілка прямого `print("...")` УНІФІКОВАНА із загальним шляхом
   (одна логіка для літералу й змінної, перевірено побайтово - вивід
   не змінився). Арифметика/порівняння над рядками (навіть ==/!=) -
   явна помилка компіляції: content-порівняння (strcmp) ще не
   реалізовано, і незрозуміло, чи identity-порівняння (просто адреси)
   збіглось би з тим, як порівнює рядки VM - чесна відмова краща за
   неперевірену поведінку.

   **Масиви** (`ValType.Array`, вказівник-eax): `[довжина:4][padding:
   4][елементи по 8 байтів]`. СПРОЩЕННЯ - лише Number-елементи (немає
   tagged union для змішаних типів). Літерал `[1,2,3]`, читання
   `arr[i]`, запис `arr[i] = x` - усе живцем перевірено проти VM,
   побайтовий збіг (включно з накопиченням суми в циклі). БЕЗ
   перевірки меж (вихід за межі читає/пише поза блоком) - відоме,
   свідомо не виправлене обмеження. print(масив) напряму, арифметика/
   порівняння над САМИМ масивом - явна помилка (індексуйте arr[i]).

   **Ціль --target nyxos**: рядки й масиви поки працюють ЛИШЕ для
   --target linux - у ABI NyxOS ще немає syscall'у виділення пам'яті
   (потрібного для heap_alloc) - чесна помилка компіляції замість
   мовчазної поломки на реальній NyxOS. Живий тест УСЕРЕДИНІ NyxOS - і
   для дробових чисел (попередній пункт), і для рядків/масивів -
   лишається окремим наступним кроком (Фаза N6).

   **Структури** ✅ ЗАВЕРШЕНО, ЛИШЕ ПОЛЯ (14.09.2026). `var p =
   Struct { field: value, ... }`, читання/запис `p.field` - живцем
   перевірено проти VM, побайтовий збіг. Offset полів обчислюється
   ОДИН РАЗ на весь файл (структури - верхній рівень, не всередині
   функцій). СПРОЩЕННЯ: лише Number-поля, ВСІ поля - явно (без
   значень за замовчуванням). Методи (func Struct.method - функція з
   неявним self) і успадкування (extends/super) - СВІДОМО НЕ
   реалізовано цим бекендом (чесна помилка компіляції при спробі) -
   суттєво більший обсяг, ніж самі поля, і по суті вже НАЛЕЖИТЬ Фазі
   N4 (методи/виклики - близькі до замикань за складністю диспетчеризації).
10. `==`/`!=` з тим самим правилом, що вже задокументовано в
    tests/test_equality.nx (2 == 2.0 - true, порівняння за ЗНАЧЕННЯМ,
    не за "коробкою").

## Фаза N4 — Замикання, винятки, збирання сміття

10.5. **Методи структур** ✅ ЗАВЕРШЕНО (15.09.2026) - `obj.method(args)`,
    неявний `self` (перший параметр - той самий підхід, що вже дає
    Parser.cs: self - звичайний FunctionParameter із Type=ім'я
    структури). Кожен метод - під унікальною міткою
    "StructName__methodName". РЕАЛЬНИЙ баг, знайдений живим тестом:
    Parser.cs зберігає ПОВНЕ ім'я методу як "StructName.methodName" у
    FunctionDeclaration.Name - перша версія шукала за "голим" іменем і
    завжди провалювалась. Живцем перевірено проти VM - побайтовий
    збіг. СПРОЩЕННЯ: аргументи/поля/повернення - лише Number, лише
    --target linux (як і структури взагалі).

11. Замикання (`var f = func(){...}`) ✅ ЗАВЕРШЕНО, ЗІ СПРОЩЕННЯМ
    (15.09.2026) - без CLR-делегатів: явна структура "вказівник на код
    + вказівник на захоплене оточення" (той самий підхід, що C++
    лямбди компілюються в machine code). Живцем ЗВІРЕНО з VM (не
    здогадка!) - `tests/test_closures.nx` явно показав, що захоплення
    в НАЯВНІЙ VM - ЗА ЗНАЧЕННЯМ (знімок на момент створення), а НЕ за
    посиланням, як спершу читалось з селфхост-інтерпретатора (окрема,
    ІНША реалізація мови, не той самий VirtualMachine.cs) - власний
    тест підтвердив ще й, що мутація ВСЕРЕДИНІ тіла НЕ зберігається
    між викликами того самого замикання. Реалізовано як "копія в
    env-блок на купі при СТВОРЕННІ + копія з env у ЗВИЧАЙНІ локальні
    слоти на ПОЧАТКУ КОЖНОГО виклику" - жодної непрямої адресації при
    читанні/записі всередині тіла не треба (захоплена змінна - просто
    ще один локальний слот). 2 РЕАЛЬНІ баги знайдено й виправлено:
    (1) env-вказівник при виклику передавався звичайним 4-байтовим
    `push` замість уніфікованого 8-байтового слота - зсувало ВСІ інші
    параметри; (2) вкладена лямбда, якій потрібна змінна з
    "дідівської" (не безпосередньо охоплюючої) області - виявлення
    вільних змінних не поширювало захоплення транзитивно, виправлено
    стандартним closure-conversion підходом. СПРОЩЕННЯ: замикання -
    лише як локальна змінна (створити й викликати), НЕ як аргумент
    функції й НЕ як return зі звичайної функції (знадобився б
    статичний вивід типу РЕЗУЛЬТАТУ довільного виклику, а не
    універсальне "усі функції - Number"); захоплювати можна лише
    Number-змінні; лише --target linux (потрібен heap_alloc).
12. `try`/`catch`/`throw` ✅ ЗАВЕРШЕНО (15.09.2026) - БЕЗ CLR exceptions:
    ручний setjmp/longjmp-стиль. 16-байтовий "кадр обробника" на стеку
    ФУНКЦІЇ для кожного try (saved_esp, saved_ebp, catch_label,
    prev_handler_ptr), зв'язаний список через глобальний exc_top -
    throw не знає, скільки функцій викликано між try і throw (той
    самий трюк, що справжній C setjmp/longjmp). Неперехоплений throw -
    чесний аварійний вихід (код 1), а НЕ спроба продовжити ніби нічого
    не сталось. СПРОЩЕННЯ: throw лише Number-значення (catch-змінна
    статично типізована як Number завжди); return/break/continue З
    СЕРЕДИНИ try/catch - явна помилка компіляції (обробник не
    деактивувався б коректно на такому шляху виходу). Живцем
    перевірено проти VM (простий throw/catch, вкладені try, throw в
    циклі з продовженням ітерацій, неперехоплений throw) - побайтовий
    збіг. Працює для ОБОХ цілей (linux/nyxos) - на відміну від
    рядків/масивів/структур/замикань, не потребує heap_alloc.
13. Збирання сміття - СВІДОМО ВІДКЛАДЕНО (найчесніший вибір, як і
    планувалось тут): почато БЕЗ нього (просто "текти" - прийнятно
    для коротких/скриптових програм), справжній GC (mark-sweep чи
    проста лічба посилань) - окремий, значний майбутній крок, НЕ
    блокує решту плану. Це ЗАВЕРШУЄ Фазу N4.

  -fno-stack-protector -fno-pie -O2` для кожного `.c` окремо в `.o`,
  потім ОДИН `ld -m elf_i386 -T src/linker.ld` лінкує ВСІ `.o`
  (30+ штук) разом у Multiboot ELF (`build/nyxos.bin`, база 1M/0x100000).
  Виклик - звичайнісінький cdecl (жодних `__attribute__((interrupt))`/
  `regparm`/`fastcall` у всьому `src/` - навіть ISR - `isr.s` сам
  зберігає регістри вручну й викликає ЗВИЧАЙНІ cdecl C-функції).
- НІЯКОГО механізму динамічного підключення КОДУ немає (grep на
  dlopen/plugin/elf_load/foreign - нуль збігів) - єдиний шлях
  "підключити" щось нове - додати ще один `.o` у той самий `ld`-виклик
  поряд з рештою.
- Найпростіший кандидат на "перший переписаний модуль" (менший і
  простіший, ніж gconsole.c): `src/kstring.c` (1061 байт) - 4 функції,
  ЧИСТА логіка з покажчиками (жодних глобальних змінних, апаратних
  портів, вбудованого асемблера, структур/бітових полів):
  `size_t k_strlen(const char*)`, `int k_streq(const char*, const char*)`,
  `int k_starts_with(const char*, const char*)`,
  `void k_strcpy(char*, const char*, size_t)`.
- Аллокатор ядра (`kheap.c`): `void* kmalloc(uint32_t size)` /
  `void kfree(void* ptr)` - класичний free-list, first-fit - якщо колись
  знадобиться виділення пам'яті З КОДУ ядра (не user-процесу), викликати
  напряму через cdecl, БЕЗ жодного syscall (ядро не робить syscall саме
  на себе).

**Ключовий висновок**: щоб переписаний шматок РЕАЛЬНО можна було
підключити до збірки ядра, компілятор має вміти породжувати не
"самостійний виконуваний файл" (як усі попередні цілі - linux/nyxos-
userspace), а **звичайний РЕЛОКОВАНИЙ .o-об'єкт** з експортованими
C-ABI-сумісними символами (`.global funcName`) - БЕЗ `_start`/`main`,
БЕЗ syscall'ів (ядро - Ring0, `int 0x80` усередині нього мало б
катастрофічно інший сенс), і що НАЙВАЖЛИВІШЕ - з правильним C ABI
(параметри - 4-байтові cdecl-слоти, а НЕ 8-байтові Number-слоти, якими
компілятор користується всюди досі; ціле число - у %eax, а не %xmm0).

19. **Нова ціль компілятора - `--target nyxos-kernel`** ✅ ЗАВЕРШЕНО
    (15.09.2026): компілює кожну функцію ВЕРХНЬОГО рівня в незалежний,
    C-ABI-сумісний символ (без main/_start - файл просто асемблюється
    в `.o`, БЕЗ лінкування - готовий додати до `ld`-виклику ядра поряд
    з рештою). Числові параметри й результат - конвертуються на межі
    (C int, 4-байтовий cdecl-слот <-> внутрішній Number/double, %xmm0)
    РІВНО ОДИН РАЗ на вході/виході - решта тіла компілюється ЗВИЧАЙНИМ,
    уже перевіреним Number-шляхом без жодного нового коду. Рядкові
    параметри - вже готовий покажчик (String і так завжди був
    `char*`-сумісним представленням). Bool-результат (напр.
    `return a[i] == b[i]`) - уже 0/1 у %eax після setCC, той самий
    формат, що C int, без конвертації. СПРОЩЕННЯ ПЕРШОГО кроку: без
    викликів інших функцій зсередини (уникає проблеми "яка КОНКРЕТНО
    calling convention в іншої функції" - kstring.c й так не мав
    внутрішніх викликів), без print()/try-catch/масивів/структур/
    замикань (потребували б syscall'ів чи heap_alloc, яких у Ring0
    просто немає в такому вигляді).
20. **Індексація рядка `s[i]`** ✅ ЗАВЕРШЕНО - читання (БАЙТ 0-255 за
    позицією, потрібно для "поки s[i] != 0") і ЗАПИС (`s[i] = ...`,
    потрібно для k_strcpy) - запис ЛИШЕ для `--target nyxos-kernel`
    (для інших цілей String - завжди вказівник на .rodata, запис туди
    впав би на read-only сторінці).
21. **Живий доказ концепції** ✅ ЗАВЕРШЕНО й ПІШЛО ДАЛІ, НІЖ планувалось
    (15.09.2026): усі 4 функції РЕАЛЬНОГО `src/kstring.c` з репозиторію
    NyxOS переписані мовою NyxilumLang (`k_strlen`, `k_streq` -
    ТОЧНА відповідність оригінальному алгоритму, `k_starts_with`,
    `k_strcpy` - зі збереженням нюансу з коментаря в C-оригіналі:
    ЗАВЖДИ NUL-термінує результат, навіть при обрізанні). Спершу
    перевірено окремим freestanding C-тестом (gcc -m32 -ffreestanding
    -nostdlib, БЕЗ libc, БЕЗ NyxOS) - усі 7+ перевірок пройшли, включно
    з крайовими випадками k_strcpy. **ПОТІМ - справжня інтеграція**:
    kstring.o (скомпільований NyxilumLang) підмінено замість
    оригінального в РЕАЛЬНІЙ збірці ядра NyxOS (build.sh), перелінковано
    й завантажено в QEMU - **знайдено й виправлено РЕАЛЬНИЙ баг**: ядро
    падало з Invalid Opcode одразу після ініціалізації файлової
    системи, бо NIXOS ніколи не вмикав SSE2 (CR0.EM/MP, CR4.OSFXSR) -
    а весь код компілятора представляє числа як double через SSE2.
    Виправлено в самому NyxOS (`src/kernel.c::enable_sse()`, окремий
    коміт у репозиторії NyxOS) - стандартна, безпечна практика,
    потрібна БУДЬ-ЯКОМУ майбутньому kernel-target коду, не лише
    kstring.c. Після фіксу - ядро із NyxilumLang-переписаним kstring.o
    завантажується ІДЕНТИЧНО до оригінального (побайтово той самий
    серійний лог аж до готовності shell). **Це перший файл ядра NyxOS,
    ПОВНІСТЮ переписаний мовою NyxilumLang і підтверджено робочий у
    справжньому ядрі**, а не лише в ізольованому тесті.

## Фаза N8 — Примітиви для реальних модулів ядра (16.09.2026)

За прямою вказівкою Sviatoslav'а ("треба розширювати... і повністью
перепиши NyxOS на NyxilumLang") - реалізація примітивів, які
"Обстеження кандидатів на третій модуль" вище (умовно назване N8 ще
тоді) визначило як блокуючі для kheap.c/pkg.c/auth.c. Три окремі,
ПОВНІСТЮ незалежно перевірені коміти:

26. **Побітові оператори (`& | ^ << >>`, унарний `~`) - МОВНА фіча**
    ✅ ЗАВЕРШЕНО - у ВСІХ трьох шляхах одразу (Lexer/Parser/AST не
    потребували змін для AST - BinaryExpression вже зберігає оператор
    як рядок; байткомпілятор+VM; нативний x86). Пріоритети - C-подібні
    (`|` слабший за `^`, слабший за `&`, слабший за `==`; `<<`/`>>` між
    порівняннями й `+`/`-`). У VM - конвертація через `(int)` (32-
    бітне знакове ціле). У нативному компіляторі - той самий трюк, що
    вже дає `%` (mod): `cvttsd2si` округлює ОБИДВА double-операнди в
    32-бітні GPR, `and`/`or`/`xor`/`shl`/`sar` (НЕ `shr` - зі знаком,
    як VM), `cvtsi2sd` назад; лічильник зсуву - обов'язково в `%cl`.
    **РЕАЛЬНИЙ БАГ, знайдений власним тестом на пріоритет** (не
    теоретичний): `"6 & (5==4)"` дало `4` замість `0` у нативному
    компіляторі - `CompileNumberBinary` безумовно припускав, що ПРАВИЙ
    операнд теж Number (у `%xmm0`), а Bool-результат (`==`/`!=`/`<`/
    `&&`) лежить у `%eax` - без явної конвертації код читав СМІТТЯ з
    `%xmm0`. Виправлено: конвертація `%eax`->`%xmm0` через `cvtsi2sd`,
    якщо правий операнд НЕ Number - виправляє ВСІ оператори
    `CompileNumberBinary` (не лише нові побітові) для будь-яких
    змішаних Number/Bool виразів. Перевірено: новий `tests/
    test_bitwise.nx` (VM, 67/67 повна регресія), `compile-native
    --target linux` на ТОМУ САМОМУ наборі значень - побайтовий збіг з
    VM ДО і ПІСЛЯ фіксу (перше виявило баг, друге підтвердило).
27. **`peekNum`/`peekPtr`/`pokeNum`/`pokePtr` + арифметика вказівників
    (`ptr + N`/`ptr - N`)** ✅ ЗАВЕРШЕНО - ЛИШЕ `--target nyxos-kernel`
    (компілятор-інтринзики, НЕ зовнішні символи). Мова досі не має
    справжніх вказівників/структур-як-сирої-пам'яті (повна система
    типів-вказівників - окрема, значно більша робота) - замість неї
    МІНІМАЛЬНИЙ, достатній примітив: "поле" у пам'яті - просто
    (базова_адреса + зсув), peek/poke читає/пише РІВНО 4 байти там.
    ЧОТИРИ окремі функції (не одна) - статичний ТИП результату (Number
    для size/flags, String для вказівникових полів типу "next")
    компілятор мусить знати НАПЕРЕД (`InferExprType`), а не вгадувати.
    `"ptr + N"` зсуває на N БАЙТІВ (як `char*` у C, НЕ як `T*` з
    масштабуванням - масштаб рахує сам `.nx`-код множенням, як
    оригінальний `kheap.c` уже робить руками для `sizeof(...)`).
    Перевірено живцем через freestanding C-гарнес (той самий підхід,
    що kstring.c): `setup()` виділяє блок через `kmalloc`, пише 2 поля
    + вказівник "next" на себе самого, 5 перевірок (поля, читання
    через next, зміни через peek+poke) - усе пройшло. **РЕАЛЬНА
    пастка під час тестування** (власна помилка, НЕ баг компілятора):
    параметри kernel-функцій БЕЗ явного `: string` типізуються як
    Number за замовчуванням (той самий нюанс, що вже задокументовано
    в item 19-21) - без анотації `"ptr + N"` тихо йшов би в
    `CompileNumberBinary` замість нового шляху арифметики вказівників.
28. **Порівняння вказівників (`==`/`!=`) - ідентичність адрес** ✅
    ЗАВЕРШЕНО - ЛИШЕ для `--target nyxos-kernel`. Спроба РЕАЛЬНО
    перекласти `kheap.c` (нижче) одразу показала: без `"current == 0"`/
    `"current != 0"` (null-перевірки) неможливо написати ЖОДНОГО
    зв'язного списку. String зліва, String АБО Number (звичайний
    літерал `0` для "порівняй з null") справа - пряме `cmp` сирих
    `%eax`-значень (ідентичність, НЕ `strcmp`-подібний вміст).
    Перевірено живцем (той самий freestanding-гарнес підхід):
    `is_null(0)`/`is_null(&x)`/`not_null(...)`/`same_ptr(&x,&x)`/
    `same_ptr(&x,&y)` - усі 6 перевірок пройшли. ЧЕСНО
    задокументовано, НЕ виправлено: `"Number == String"` (Number
    ЗЛІВА) не підтримується - диспетчер перевіряє тип ЛІВОГО операнда
    першим; на практиці не проблема, бо C-подібний стиль завжди пише
    `"pointer == 0"`, не навпаки.

**Спроба РЕАЛЬНОГО перекладу `kheap.c` (16.09.2026) - ЧЕСНИЙ висновок,
ще ОДИН блокер, глибший за попередні.** Маючи всі три примітиви вище,
почав перекладати `kheap.c` дослівно - і одразу вперся у ДВІ проблеми:

1. **Функції, визначені в самому `.nx`-файлі, ЗАВЖДИ трактуються як
   такі, що повертають Number** (`CallExpression => ValType.Number` -
   спрощення ще Фази N3, застосовується ПОВСЮДИ, не лише kernel-
   target). `kmalloc`-подібна ВЛАСНА функція (наприклад, переклад
   `request_space()`/`kmalloc()` самого `kheap.c`) МАЄ повертати
   покажчик (String) - але виклик такої функції компілятор все одно
   вважав би Number, і конвертував би сирий покажчик з `%eax` через
   `cvtsi2sd` НІБИТО в double - СПОТВОРЮЮЧИ адресу в безглузде число.
   Це ГЛИБШЕ за прості "додати ще одну можливість" - потрібне
   СПРАВЖНЄ виведення типу результату функції (аналіз `return`-
   операторів кожної функції НАПЕРЕД, а не universal "усі Number") -
   міняє логіку, яку використовує ВЕСЬ компілятор (усі цілі, не лише
   kernel), а не лише kernel-специфічний шматок.
2. **Глобальна змінна типу String НЕ може стартувати як "null"**:
   ініціалізатор глобальної МАЄ бути сталим літералом (item 19-21), а
   рядковий літерал (напр. `""`) компілюється в АДРЕСУ реального
   (нехай і порожнього) рядка в `.rodata` - НЕ бітовий патерн 0.
   Обхідний шлях ІСНУЄ (окремий `bool`-прапорець "чи є перший блок"
   замість покладатись на null-адресу), але для локальних змінних і
   ЗНАЧЕНЬ, ЩО ПОВЕРТАЮТЬ ФУНКЦІЇ, ця проблема НЕ виникає (звичайний
   `var x = 0` усередині функції не має обмеження "сталий літерал") -
   лише П.1 вище (типи результатів функцій) - СПРАВЖНІЙ, широкий
   блокер.

**Наступний крок для kheap.c конкретно:** справжнє виведення типу
результату функції (не universal Number) - дозволить `.nx`-функціям
повертати String (покажчик), як і зовнішнім kmalloc/kernel-функціям
уже дозволено. Це осмислений, окремо оцінюваний шматок роботи, який
торкається ЯДРА компілятора (усіх цілей), а не лише kernel-target -
свідомо НЕ форсується сьогодні напівробочим обхідним рішенням.

**ВИПРАВЛЕНО (16.09.2026): "структура не має методу" для методів,
оголошених ПОЗА тілом `struct {...}`.** Раніше знайдений, але не
виправлений баг (item 26 вище лише зауважив, що він існує ще на
попередньому коміті). Причина: `Parser.cs::ParseFunctionDeclaration`
парсить `func Struct.method(...)` ОДНАКОВО незалежно від того, чи ця
декларація лежить усередині тіла `struct {...}`, чи як звичайна
декларація верхнього рівня - в обох випадках виходить
`FunctionDeclaration` із `Name = "Struct.method"`. Compiler.cs
(VM-шлях) реєструє функції за повним іменем незалежно від джерела,
тому обидва синтаксиси там завжди працювали однаково. `NativeCodegen.cs`
натомість збирав таблицю методів (`_structMethods`) ЛИШЕ зі
`StructDeclaration.Methods` (методи, оголошені всередині тіла) -
метод, оголошений ПОЗА тілом структури, у цю таблицю не потрапляв
узагалі, і виклик такого методу падав з "структура не має методу",
хоча він там БУВ. Фікс: `Compile()` тепер додатково збирає top-level
`FunctionDeclaration` із крапкою в імені й домішує їх у `_structMethods`
за іменем структури-власника (до крапки); цикл компіляції звичайних
функцій виключає ці ж декларації (щоб не компілювались ДВІЧІ - і як
"метод" під міткою `StructName__methodName`, і як звичайна функція під
зламаною міткою з крапкою). Перевірено живцем проти VM: репро з задачі
(`Point.dist2()` поза тілом структури) і змішаний файл (метод усередині
тіла + метод поза тілом + метод, оголошений ПІСЛЯ `main()`) - побайтовий
збіг виводу з VM в обох випадках. 67/67 регресійних тестів (VM) - без
регресій.

**ВИПРАВЛЕНО (18.09.2026): явна анотація результату kernel-функції
(`-> string`) тепер РЕАЛЬНО враховується.** Це і був той самий блокер
kheap.c з item 28 (спроба РЕАЛЬНОГО перекладу) - "функції, визначені в
самому .nx-файлі, ЗАВЖДИ вважаються такими, що повертають Number".
Виявилось, що робити повноцінний вивід типу з потоку керування
(аналіз усіх `return` НАПЕРЕД, як спершу здавалось потрібним) -
НЕПОТРІБНО: `Parser.cs` ВЖЕ давно парсить `func f(...) -> string {...}`
у `FunctionDeclaration.ReturnType`, просто `NativeCodegen.cs` це поле
НІКОЛИ не читав. Фікс - `KernelReturnTypeFromAnnotation()`: та сама
таблиця типів, що вже й для kernel-параметрів (string -> вказівник,
i32/f64/number/... -> Number, bool -> Bool), застосована на ДВОХ
місцях - `InferExprType(CallExpression)` (щоб виклик такої функції
десь ще коректно бачив її тип) і сам виклик у `CompileExpression`
(щоб результат НЕ конвертувався `cvtsi2sd` як завжди-Number). Без
анотації - старий типовий Number, ЖОДНА раніше робоча kernel-функція
не ламається. Додано й перевірку узгодженості: якщо анотація Є, а
РЕАЛЬНЕ значення в `return` - іншого типу, компілятор тепер каже про
це прямо, а не мовчки вірить анотації.

Дорогою знайдено ЩЕ ОДИН реальний, суміжний недолік (живим тестом на
самому цьому фіксі): `InferExprType` для `BinaryExpression` не знав,
що `рядок + число`/`рядок - число` (арифметика вказівників, Фаза N8)
дає `String` - сам КОДОГЕН це вже правильно компілював, але
ТИП-ВИВІД досі мовчки казав "Number" для будь-якого `+`/`-` - тому
`func f(p: string) -> string { return p + 1 }` одразу впав би на
щойно доданій перевірці узгодженості. Виправлено тим самим правилом
(String зліва + Number справа, лише kernel-target, лише +/-), що вже
є в самій компіляції.

Перевірено живцем (freestanding C-гарнес, як і решта Фази N8):
`make_ptr(base, offset) -> string { return base + offset }`,
викликаний з `store_at`/`load_at` (обидва пишуть/читають через
повернутий вказівник через `pokeNum`/`peekNum`) - `store_at(buf,4,111)`
+ `store_at(buf,8,222)`, потім `load_at(buf,4)==111` і
`load_at(buf,8)==222` - обидва пройшли. Це РІВНО той сценарій, що
раніше блокував kheap.c (функція, що ОБЧИСЛЮЄ й ПОВЕРТАЄ вказівник).
Регресій нуль: 67/67 (VM) + всі наявні kernel-модулі
(`native-examples/nyxos-kernel/*.nx`) досі компілюються без змін у
виводі.

**ВИПРАВЛЕНО (18.09.2026, той самий день): другий блокер kheap.c - глобальний
null-покажчик - виявився ТІЄЮ Ж прогалиною, що й ReturnType вище.**
`Parser.cs` вже давно парсить `var x: string` (тип БЕЗ ініціалізатора -
`VariableDeclaration.TypeAnnotation`), `NativeCodegen.cs` для kernel-
глобальних це поле теж НІКОЛИ не читав - без ініціалізатора тип
завжди був Number (`.double 0.0`). Задокументований обхід (окремий
bool-прапорець "чи вже є перший блок") виявився НЕПОТРІБНИМ - досить
було прочитати `TypeAnnotation`, коли ініціалізатора нема: `string` ->
`.long 0` (СПРАВЖНІЙ нульовий вказівник, не вказівник на порожній
рядок - інакше `p == 0`-перевірка з Фази N8 завжди хибна), `bool`/

`set_head(p)`, `get_head()` повертає ту саму адресу - код виходу 0.

Дорогою додано ще ОДИН мінімальний kernel-інтринзик - `numToPtr(n)`

меж/переповнення), а вказівником вона стає РІВНО В ОДНІЙ точці - коли
з неї треба зробити реальний заголовок блоку (той самий принцип
"конвертація один раз на межі", що вже застосований для kernel-

## Фаза N8.5c/d (18.09.2026, той самий день) - адреса функції, непрямий виклик, портовий I/O

Три нові примітики компілятора одразу, ЗАРАДИ `pci.c` (фундаментальний
модуль NyxOS - на ньому тримається `pci_scan()`/`pci_find_device()`,
якими користуються rtl8139.c/ahci.c/uhci.c/settings.c):

1. **"Гола" назва функції (без виклику) = її АДРЕСА** (`var cb =
   my_func`) - `InferExprType(VariableExpression)` тепер перевіряє,
   чи ім'я не змінна, а ВІДОМА функція цього файлу (`_knownFunctions`)
   - тоді результат `ValType.String`; кодоген - `mov $funcName, %eax`
   (мітка функції УЖЕ валідна адреса коду - kernel-функції й так
   експортуються під власним іменем як `.global funcName`, жодного
   нового механізму не треба). Потрібно, щоб передати callback ЗОВНІ
   (`pci_scan(find_uhci_callback)`).
2. **Непрямий виклик через ЗНАЧЕННЯ** (`cb(arg)`, де `cb` -
   String-параметр/змінна, а НЕ відома функція) - розпізнається за
   тим самим принципом, що вже дає `isClosureVar` для VM-шляху:
   `call.FunctionName` - НЕ в `_knownFunctions`, АЛЕ ЄСТЬ у
   `_varTypes`/`_globalVars` з типом String - тоді аргументи
   компілюються ЗВИЧАЙНО (push у зворотньому порядку), значення
   callback'а завантажується ОСТАННІМ (щоб не затерти вже
   запушені аргументи), і виклик - `call *%eax` (непрямий, через
   регістр), а НЕ `call funcName` (пряме ім'я символу). Потрібно,
   щоб САМА функція (`pci_scan`) могла викликати переданий їй
   callback.
3. **Портовий ввід-вивід** (`inb`/`inw`/`inl`/`outb`/`outw`/`outl`) -
   компілятор-інтринзики (як peek/poke), генерують сирі x86
   `in`/`out` інструкції напряму (номер порту - в `%dx`, значення -
   в AL/AX/EAX залежно від розміру; для `inb`/`inw` `%eax` явно
   обнуляється ПЕРЕД інструкцією - апаратура сама верхні байти НЕ
   чіпає). Потрібні pci.c-подібному коду (і майже КОЖНОМУ файлу, що
   торкається заліза напряму - timer.c/rtc.c/keyboard.c/vga.c/ata.c,
   ще ~20 лишається).

**Перевірка (18.09.2026)** - трьома незалежними способами, різними
для різних примітивів (портовий I/O - ПРИВІЛЕЙОВАНІ інструкції,
ізольований freestanding-гарнес на голому Linux-процесі їх НЕ
виконає без root - тому verification-метод тут інакший, ніж для
попередніх фаз):
1. Freestanding C-гарнес (той самий підхід, що завжди) - функція
   бере адресу СВОЄЇ функції, передає зовнішньому C `invoke_callback`,
   яка РЕАЛЬНО викликає її через `void*`-каст - підтверджено коректний
   round-trip (NyxilumLang -> C -> NyxilumLang -> C).
2. Другий C-гарнес - функція ОТРИМУЄ callback ПАРАМЕТРОМ і сама його
   викликає непрямо (точний аналог `pci_scan`) - той самий успіх.
3. **`pci.c` ПОВНІСТЮ перекладено** (`native-examples/nyxos-kernel/
   pci.nx` - `pci_make_address`/`pci_config_read32`/`
   pci_config_write32`/`read_device`/`pci_scan`/`pci_find_device`,
   усі публічні символи з pci.h) і живцем ПІДМІНЕНО в РЕАЛЬНУ збірку
   ядра NyxOS - `lspci` дала РЕЗУЛЬТАТ, БАЙТ-У-БАЙТ ІДЕНТИЧНИЙ
   оригінальному C (ті самі 6 пристроїв, ті самі vendor/device/
   bus:device:function), і `usbenum` (яка всередині `uhci_init()`
   викликає `pci_scan(find_uhci_callback)`, C-функцію з ІНШОГО файлу
   - callback переданий і викликаний повністю МІЖ файлами) відпрацювала
   штатно - реальне підтвердження, що обидва патерни використання
   `pci_scan` (широке сканування з C-колбеком, і цільовий пошук під
   час сканування) працюють через NyxilumLang-переклад так само, як
   оригінальний C. Розкладка `pci_device_t` (40 байтів, конкретні
   зсуви всіх полів) заздалегідь підтверджена НЕЗАЛЕЖНО через
   freestanding `_Static_assert` ПЕРЕД перекладом, а не здогадкою.

Регресій нуль: 67/67 (VM). Перекладені модулі ядра дотепер: kstring.c,
gconsole.c, kheap.c, pkg.c, pci.c - 5 з ~30. `auth.c` (третій
кандидат з обстеження 15.09.2026) лишається ЧАСТКОВО заблокованим -
"адреса функції як значення" тепер Є, але реєстрація callback'а через
`keyboard_set_handler` і `__asm__("hlt")` (сирий inline asm) досі
потребують окремої підтримки.

## Фаза N8.5e (18.09.2026, той самий день) - hlt(), auth.c повністю перекладено

Останній блокер `auth.c` з обстеження 15.09.2026 - `__asm__ volatile
("hlt")` у `read_line()` (спати до наступного переривання, а не
крутити CPU в холостому циклі, поки чекаємо натискання клавіші).
"Реєстрація callback'а через `keyboard_set_handler`" (другий блокер,
позначений у Фазі N8.5c/d) виявилась НЕ окремою проблемою - це
ЗВИЧАЙНИЙ виклик зовнішньої C-функції (`keyboard_set_handler`,
визначена в keyboard.c) з одним аргументом-адресою функції; Фаза
N8.5c вже навчила `CompileExpression(VariableExpression)` віддавати
адресу відомої функції в `%eax`, і ЦЕЙ шлях ЗАГАЛЬНИЙ - working для
БУДЬ-ЯКОГО виклику (внутрішнього чи зовнішнього), не лише для
`isIndirectCall`. Тобто лишався РІВНО один примітив.

1. **`hlt()`** - НОВИЙ інтринзик компілятора, той самий клас, що
   `inb`/`outb` (Фаза N8.5d): без аргументів, "повертає" 0
   (результат ніде не використовується - викликається лише заради
   побічного ефекту). Кодоген - рівно одна сира інструкція `hlt`.
   Як і портовий I/O, це ПРИВІЛЕЙОВАНА інструкція (Ring0-only,
   викликає #GP у звичайному unprivileged Linux-процесі незалежно
   від IOPL) - ізольований freestanding-гарнес принципово НЕ може
   її перевірити; єдиний спосіб верифікації - реальна підміна в
   ядрі NyxOS і живий QEMU-тест.

2. **`auth.c` повністю перекладено** (`native-examples/nyxos-kernel/
   auth.nx`) - `auth_char_handler`/`read_line`/`simple_hash`/
   `create_account`/`login_prompt`/`auth_run`, усі публічні символи
   з auth.h. Розкладка `user_record_t` (36 байтів: username[0..31],
   password_hash за зсувом 32) заздалегідь підтверджена НЕЗАЛЕЖНО
   через freestanding `_Static_assert`, як і для pci.c.

   **ЧЕСНА, свідома розбіжність із оригінальним C**: `simple_hash()`
   тут - той самий FNV-1a за ФОРМОЮ (XOR потім множення), АЛЕ з явним
   маскуванням акумулятора до 24 біт (`& 0xFFFFFF`) на КОЖНІЙ
   ітерації, замість повного 32-бітного unsigned-переповнення
   оригіналу. Причина - той самий клас пастки, що вже задокументовано
   для `pci.c`'s `1 << 31` (Фаза N8.5c/d, коментар про
   0x80000000): побітові оператори (`& | ^ << >>`) конвертують
   double->int32 через `cvttsd2si` ПЕРЕД самою операцією - для
   значень ПОЗА знаковим int32-діапазоном (>2^31-1) SSE2 дає
   "невизначене значення" (0x80000000) замість справжніх нижніх 32
   бітів. Повне 32-бітне unsigned-переповнення (де проміжні значення
   регулярно перетинають цю межу) наразі непредставиме коректно в
   Number-моделі цього компілятора (double, з переходом в int32
   лише в момент побітової операції) - потрібна була б ОКРЕМА
   64-бітна чи явно unsigned-int арифметика, яких мова не має. 24-
   бітний акумулятор і множник 97 підібрані так, щоб (2^24-1)*97 ≈
   1.63e9 НІКОЛИ не наближався до межі 2^31-1 - жодна проміжна
   величина не потрапляє в небезпечну зону. Наслідок: users.dat,
   створений оригінальним `auth.c`, не автентифікує через цю
   NyxilumLang-версію і навпаки - але створення+вхід САМІ ПО СОБІ
   повністю самоузгоджені (та сама `simple_hash` і при створенні
   акаунту, і при вході), що й перевірено живцем нижче. Сам
   оригінальний C-хеш і так задокументований як "НЕ криптографічний,
   лише щоб пароль не лежав відкритим текстом" - ця зміна не
   послаблює й не посилює реальну загрозу.

**Перевірка (18.09.2026)** - двома незалежними способами:
1. Ізольований freestanding C-гарнес ЛИШЕ для `simple_hash()`
   (привілейовані `hlt`/`keyboard_set_handler`-шляхи він перевірити
   не може) - той самий вхід дає той самий вихід, різні входи дають
   різний хеш, і НАЙГОЛОВНІШЕ - довгий (99-символьний) пароль НЕ
   вибив акумулятор за межі 24 біт (перевірка на кожному кроці).
2. **Повний живий цикл через РЕАЛЬНУ підміну в ядрі** (найпереконливіший
   тест з усіх auth-подібних сценаріїв дотепер): `build/auth.o`
   підмінено на NyxilumLang-версію в справжній збірці, QEMU headless
   з HMP-монітором (той самий unix-socket-метод, що й раніше), фізичні
   натискання клавіш через `sendkey` (включно з `shift-<літера>` для
   ВЕЛИКИХ літер - потрібно для `nyxinstall`'s "TAK"-підтвердження),
   а перевірка екрана - НЕ screendump/OCR, а пряме читання VGA
   текстового буфера (`pmemsave` на фізичну адресу 0xB8000, 4000
   байтів = 80x25 символів), декодоване через власну таблицю
   `cyr_map` з `vga_cyr_font.h` (кирилиця в NyxOS - не CP866/UTF-8, а
   власний байт-код на гліф) - точніший метод, ніж попередні
   screendump-скріншоти, для суто текстових сценаріїв. Повний
   сценарій в ОДНОМУ завантаженні: `nyxinstall 100` -> `TAK` ->
   `diskmount` (диска ще нема користувачів - `create_account()`) ->
   ввід "sviat"/"secret1" (пароль ЗАМАСКОВАНО зірочками на екрані,
   підтверджуючи `mask_input`) -> "Обліковий запис створено" ->
   ПОВТОРНИЙ `diskmount` (той самий диск, users.dat вже існує -
   `login_prompt()`) -> НЕВІРНИЙ пароль -> "Невірне ім'я користувача
   чи пароль. Спробуй ще раз." (цикл коректно ПОВЕРТАЄТЬСЯ до
   "Ім'я користувача:", не падає і не пропускає) -> ВІРНИЙ пароль ->

   відпрацював штатно (підтверджує, що `keyboard_set_handler`

   `build/auth.o` відновлено до оригінального C одразу після тесту

## Фаза N8.5f (18.09.2026, той самий день) - timer.c: перший модуль-обробник IRQ

Сьомий перекладений модуль ядра, і ПЕРШИЙ, що САМ РЕЄСТРУЄ себе як
живий обробник апаратного переривання (IRQ0, через `isr_register_
handler`), а не лише викликається кимось іншим на вимогу - раніше
перекладені модулі (навіть pci.c/auth.c з їхніми callback'ами) завжди
виконувались у відповідь на конкретну команду shell, timer.c ж працює
БЕЗПЕРЕРВНО з моменту `sti` в kernel.c, і кожен тік проходить через
код, скомпільований NyxilumLang.

**Новий примітив не знадобився** - лише ОДИН запис у вже наявний
реєстр `ExternalKernelReturnTypes` (Фаза N7): `scheduler_tick`
(process.c) додано як `ValType.String`. Причина - той самий клас
пастки, що вже задокументовано для `kmalloc`: `scheduler_tick`
повертає СИРУ адресу стека (ESP) іншого процесу, яку `isr.s`
підставляє напряму - без цього запису невідома зовнішня функція за
замовчуванням проходила б крізь `cvtsi2sd` (int->double) на
поверненні, СПОТВОРЮЮЧИ біти адреси, і `timer_handler` (сам
оголошений `-> string` з тієї самої причини) повернув би isr.s
сміттєву адресу замість справжнього стека наступного процесу -
миттєвий крах ядра НА ПЕРШОМУ Ж тіку.

**Друга деталь, вирішена БЕЗ змін компілятора**: `timer_sleep_ms`
порівнює `target_ticks` через `<` (не побітову операцію, яка сама
обрізає до цілого через `cvttsd2si`) - справжнє ціле ділення C
(`(ms+9)/10`) відтворено формулою `(a - a%b)/b` (== `trunc(a/b)`, той
самий трюк, що компілятор сам використовує ВСЕРЕДИНІ codegen для
оператора `%`) - без цього ціль спала б на 1 тік довше на "рваних"
ms-значеннях, дрібна, але реальна розбіжність із оригіналом.
`timer_init`'s ділення (`PIT_BASE_FREQUENCY / frequency_hz`) окремого
трюку НЕ потребувало - подальші `&`/`>>` над divisor уже самі
обрізають дробову частину як перший крок.

**Перевірено двома способами**:
1. Ізольований freestanding C-гарнес - ЛИШЕ для чистих обчислень
   (`compute_target_ticks`/`compute_divisor`, без hlt/IRQ-частини, які
   гарнес принципово не може виконати) - усі порівняно з ЕТАЛОННИМ
   цілим діленням C, включно з крайовим випадком (divisor > 65535 при
   дуже низькій частоті - те саме 16-бітне обрізання, що й реальний
   запис у порт PIT).
2. **Справжня підміна `build/timer.o` в реальній збірці ядра + живе
   завантаження QEMU** - найризикованіший тест з усіх дотепер (не
   команда за вимогою, а обробник, що виконується на КОЖНОМУ тіку з
   раннього завантаження). Команда `multitask` (явно перемикає ДВА
   процеси через таймер) дала ТОЧНЕ очікуване чергування
   "ABBABABABABABABABABABABABABABABABABABABA" - прямий доказ, що
   передача сирої адреси ESP крізь `timer_handler`->`scheduler_tick`
   ->isr.s спрацювала коректно, а не лише "ядро не впало". `date`/
   `usbtest`/`meminfo`/`help` одразу після - усе штатно.
   `build/timer.o` відновлено до оригінального C одразу після тесту
   (та сама політика верифікації - не постійна заміна).

Регресій нуль: 67/67 (VM). Перекладені модулі ядра дотепер: kstring.c,
gconsole.c, kheap.c, pkg.c, pci.c, auth.c, timer.c - 7 з ~30.

## Фаза N8.5g (18.09.2026, той самий день) - rtc.c: перший out-параметр зі ЗМІШАНИМИ розмірами полів

Восьмий перекладений модуль ядра. Жодного нового примітиву не
знадобилось - лише акуратне застосування вже наявних. `rtc_time_t*
out` (8 байтів: `year` u16 за зсувом 0, `month`/`day`/`hour`/`minute`/
`second` - по одному байту за зсувами 2-6, підтверджено freestanding
`_Static_assert` ПЕРЕД перекладом, той самий підхід, що для
`pci_device_t`/`user_record_t`) - ПЕРШИЙ out-параметр зі ЗМІШАНИМИ
розмірами полів (попередні - лише однорідні 1- чи 4-байтові поля).

**Чому `year` НЕ записано через `pokeNum`**: `pokeNum` завжди пише
РІВНО 4 байти - для 2-байтового `year` (зсув 0) це затерло б і
`month` (зсув 2), й частину `day` (зсув 3) - реальна корупція сусідніх
полів. Замість цього `year` пишеться ДВІЧІ через вже наявний байтовий
запис `out[i] = ...` (Фаза N7, той самий механізм, що pci.c вже
використовує для 1-байтових полів): `out[0] = year & 255`, `out[1] =
(year >> 8) & 255` (little-endian, як і сам x86).

**Перевірено двома способами**:
1. Ізольований freestanding C-гарнес - ЛИШЕ конверсійна логіка
   (`bcd_to_bin`+BCD/12-годинний-PM/бінарний-режим+байтовий запис
   структури), винесена в окрему функцію, що бере сирі регістрові
   значення як АРГУМЕНТИ (не через `cmos_read`/`outb`/`inb` -
   привілейовані, гарнес принципово не може їх виконати) - звірено з
   еталонним C-алгоритмом на 5 сценаріях: звичайний 24-годинний BCD,
   12-годинний PM (година+12), межовий випадок "рівно 12 PM" (НЕ
   додається 12), бінарний режим (без BCD-конверсії взагалі), і
   дворозрядний рік 2099 (перевіряє, що ДВОБАЙТОВИЙ запис `year`
   дійсно потрібен - однобайтового вистачило б лише до 2255, але сама
   МЕХАНІКА запису в двох окремих байтах - те, що тестується). Усі
   п'ять - побайтовий збіг.
2. **Справжня підміна `build/rtc.o` в реальній збірці ядра + живе
   завантаження QEMU**: команда `date`, викликана ДВІЧІ з паузою в
   секунду, дала "2026-09-18 17:06:06" потім "2026-09-18 17:06:07" -
   РІВНО +1 секунда між викликами - переконливий доказ, що ввесь
   конвеєр (порти CMOS -> BCD-конверсія -> побайтовий запис структури
   -> форматований друк) працює коректно на РЕАЛЬНОМУ, живому
   годиннику материнської плати, не лише на статичному тестовому
   вводі. `build/rtc.o` відновлено до оригінального C одразу після
   тесту (та сама політика верифікації - не постійна заміна).

Регресій нуль: 67/67 (VM). Перекладені модулі ядра дотепер: kstring.c,
gconsole.c, kheap.c, pkg.c, pci.c, auth.c, timer.c, rtc.c - 8 з ~30.

причина НЕ в коді):** зроблено справжній ISO через `grub-mkrescue`
(`insmod all_video`/`insmod efi_gop` - на відміну від `run.sh`, який
вантажить лише multiboot без VBE) з тим самим kstring.o+gconsole.o.
Headless QEMU з CD-ROM не завантажується взагалі - падає в мережевий
iPXE-бут ("Boot failed: not a bootable disk... Booting from ROM...
iPXE"), перевірено `-boot order=d` і `-M pc -boot d` - без ефекту.
**Підтверджено ізольованим тестом**, що це відтворюється 1-в-1 із
ПОВНІСТЮ оригінальним, немодифікованим ISO NyxOS (без жодного
NyxilumLang-коду) - тобто це наявна вада середовища QEMU/CD-ROM-бута
в цьому оточенні, НЕ пов'язана з компілятором чи kernel.c. Залишено
як відкриту, чесно задокументовану прогалину верифікації - не варто
далі гнатись за нею зараз; повна поведінкова перевірка gconsole вже
зроблена ізольованим freestanding C-тестом (item 25, спосіб 1).

25b. **SSE2 у NyxOS ввімкнено** - `src/kernel.c::enable_sse()` (CR0.EM=0/
    MP=1, CR4.OSFXSR=1/OSXMMEXCPT=1), викликається першим рядком
    `kernel_main()`. Без цього БУДЬ-ЯКА SSE2-інструкція (увесь нативний
    компілятор використовує SSE2 для чисел) падає з Invalid Opcode (#UD)
    - виявлено й виправлено під час інтеграції kstring.o в реальне ядро.
    Це ЖОРСТКА передумова для будь-якого майбутнього kernel-target коду
    на NyxOS взагалі, задокументовано в NyxOS-репозиторії окремим комітом.

**Обстеження кандидатів на третій модуль (15.09.2026) - чесний
висновок: kstring.c/gconsole.c "легкі" не випадково.** Вони влучно
лягли на те, що компілятор УЖЕ вміє (чиста арифметика, рядки, масиви,
глобальні змінні). Перевірено наступних кандидатів:

- **`kheap.c`** (127 рядків, kmalloc/kfree самі) - потребує
  структури з полем-покажчиком-на-себе (`block_header_t* next`),
  приведення покажчик↔ціле (`(uint32_t) heap_break`), покажчикову
  арифметику (`block + 1` = зсув на sizeof(struct)), читання/запис
  4-байтового слова за довільним зсувом у пам'яті. Мова й компілятор
  зараз мають ЛИШЕ побайтове читання/запис рядка (`s[i]`), жодних
  структур-як-сирої-пам'яті чи адресної арифметики.
- **`pkg.c`** (55 рядків) - парсинг HTTP-відповіді, потребує
  побітових зсувів (`p[1] << 8` і т.д. для little-endian u32) і
  out-параметрів через покажчик (`uint32_t* out_offset`) - мова НЕ
  має побітових операторів ВЗАГАЛІ (підтверджено ще у Фазі N7, item
  22) і не має посилань/out-параметрів.
- **`auth.c`** (134 рядки) - НАЙгірший кандидат: `simple_hash` (FNV-1a)
  використовує XOR (`h ^= ...`) - як і зсуви, XOR НЕ має чистого
  арифметичного еквівалента (на відміну від UTF-8-декодування, де
  `& 0x1F` замінили на `% 32`); `keyboard_set_handler(auth_char_handler)`
  реєструє C-функцію як callback - потребує "адреси функції як
  значення" (NyxilumLang функції викликаються лише за іменем, немає
  `&funcname`); `__asm__ volatile("hlt")` - жодного способу вставити
  сирий asm чи навіть просто "заснути до переривання" з мови.

**Висновок:** щоб піти далі за ці два модулі, потрібна НЕ проста
трансляція файл-за-файлом, а нова фаза компілятора (умовно N8):
побітові оператори як МОВНА фіча (`& | ^ << >>`), покажчики/адресна
арифметика (`&x`, читання/запис слова за адресою, структури як сира
пам'ять), значення "адреса функції" для callback'ів, і, окремо,
доступ до портів вводу-виводу (`in`/`out`) для будь-якого файлу, що
торкається заліза напряму (timer.c/rtc.c/keyboard.c/vga.c/ata.c і
подібні - таких ще ~20). Це осмислений, оцінюваний шматок роботи, але
суттєво більший за один сеанс - свідомо НЕ форсується напівробочим
обхідним рішенням заради "третього модуля" як галочки.

**Дружній завантажувач (15.09.2026) ✅ ЗАВЕРШЕНО** - `make-iso.sh`
(репозиторій NyxOS) тепер генерує стилізований `grub.cfg`: gfxterm,
кольорова схема (light-green/black), timeout=5 з меню, три пункти
("NyxOS" / "Перезавантажити" / "Вимкнути") замість голого одного
menuentry без оформлення. Перевірено: `grub-mkrescue` збирає ISO без
помилок; `grub-script-check` підтверджує коректний синтаксис
`grub.cfg`. Живий QEMU-скріншот самого GRUB-меню НЕ вдалось зняти -
той самий наявний, підтверджено-непов'язаний з кодом QEMU/CD-ROM-бут
глюк цього середовища (вище) блокує й це; спроба через `-hda` (гібрид-
ISO як диск) також не завантажилась в цьому QEMU. Не критично - на
реальному залізі (куди й піде фінальний образ) BIOS/UEFI-бут з
флешки працює іншим шляхом, і це вже перевірено раніше (Фаза D
NyxOS-репозиторію, `README.md`).

## Фаза N10 — Коректна 32-бітна арифметика для побітових операторів (22.09.2026)

Sviatoslav's явний пріоритет (21.09.2026, відповідь на "чи може моя
мова замінити C/Assembler?" - див. [[project-nyxilum-native-compiler]]
у пам'яті): закрити по-справжньому в компіляторі прогалину, яку auth.c
(Фаза N8.5e) обійшов 24-бітною маскою замість реального фіксу.

**Корінь бага**: `&`/`|`/`^`/`<<`/`>>` конвертували double-операнди в
32-бітні GPR через звичайний `cvttsd2si` - для БУДЬ-ЯКОГО double з
|x| >= 2^31 (напр. акумулятор хешу, що зростає понад 2^31) ця
інструкція дає ФІКСОВАНИЙ "integer indefinite" патерн 0x80000000
замість обрізки до нижніх 32 бітів - уся інформація губилась ще ДО
самої операції.

**Виправлення входу**: `EmitDoubleToUInt32`/`EmitUInt32ToDouble`
(NativeCodegen.cs, біля EmitDoubleLiteral) - стандартний трюк GCC/
Clang для double<->uint32 без SSE4.1 cvttsd2usi (якої нема в базовому
SSE2): для x у [2^31, 2^32) віднімаємо 2^31 (тепер влазить у знаковий
діапазон), конвертуємо, повертаємо старший біт назад через xor;
симетрично в інший бік. Спільна константа 2^31 - одна на весь файл
(`U32ConstLabel`, лінива властивість).

**РЕАЛЬНИЙ БАГ #2, знайдений і відкочений ЖИВИМ ТЕСТОМ одразу після
першої версії фіксу** (перш ніж комітити - за встановленою в цьому
репозиторії дисципліною "спочатку живцем, потім документуй"): вихід
назад у double спочатку теж зробили "безанаковим" (EmitUInt32ToDouble)
- але це зламало СПРАВЖНІ від'ємні числа (`-8 >> 1` дало 4294967292
замість -4, бо 0xFFFFFFFC як бітовий патерн ОДНАКОВИЙ і для -4 signed,
і для 4294967292 unsigned - без реального типу-мітки неможливо
розрізнити ці два випадки на виході). Виправлено: вихід лишено
ЗВИЧАЙНИМ signed `cvtsi2sd` (як і VM - C#'s `(int)` теж signed) - для
всієх нормальних чисел (уся регресія 67/67) це ІДЕНТИЧНО старій
поведінці; великий акумулятор при прямому друку виглядатиме "зі знаком
навпаки" (3000000000 надрукується як -1294967296), АЛЕ лишається
БІТОВО коректним і самоузгодженим для будь-яких ПОДАЛЬШИХ операцій -
перевірено живцем ланцюжком `h = 3e9; h ^= 0; h &= 4294967295.0;`
двічі поспіль - `h == h2` дало `True`. Саме так реально
використовується хеш у auth.c (порівнюється й хешується далі, а не
друкується як "гарне" десяткове число) - чесно задокументовано, не
приховано.

**РЕАЛЬНИЙ БАГ #3, знайдений одразу після**: `print_double` (окрема,
незалежна функція - НЕ побітові оператори) мала ТОЙ САМИЙ корінний
cvttsd2si-баг для друку ВЕЛИКИХ ЧИСЕЛ ВЗАГАЛІ, безвідносно до
побітових операторів - `print(3000000000.0);` (без жодного `&`/`^`)
теж мовчки друкував "2147483648". Виправлено тим самим механізмом
(`EmitDoubleToUInt32` для цілої частини, `EmitUInt32ToDouble` для
дробової - тут UNSIGNED-відновлення ПРАВИЛЬНЕ, бо на відміну від
побітових операторів xmm0 тут - КОНКРЕТНЕ відоме значення, яке треба
надрукувати ТОЧНО, а не бітовий патерн з невизначеним signed/unsigned
наміром) - обидва хелпери викликаються як звичайні C#-методи прямо
всередині EmitPrintDoubleHelper (не дубльований inline-asm).
Перевірено живцем: `print(3000000000.0)` -> `3000000000.000000000000000`.

Регресій нуль: 67/67 (VM, `nyxilum_dev_test`). `--target nyxos-kernel`
перекомпіляція `auth.nx` без змін пройшла успішно (спільний кодогенер,
жодної kernel-специфічної гілки в цій частині) - АЛЕ живий QEMU-swap-
тест auth.c ПОВТОРНО НЕ РОБИВСЯ (той, що є в Фазі N8.5e, лишається
чинним підтвердженням; 24-бітна маска в auth.nx і далі там - тепер вже
НЕ обов'язкова, але прибирання й повторна жива QEMU-перевірка -
окремий майбутній крок, чесно НЕ зроблений зараз).

**Чесно про залишок ("чи може моя мова замінити C/Assembler?"
відповідь 21.09.2026)**: навіть після цієї фази - НІ, повністю ні.
Бракує (за пріоритетом): (1) справжній inline-asm (`asm{...}` з сирим
текстом інструкції) - без цього кожна нова інструкція (cpuid, lgdt,
rdtsc, lock cmpxchg...) потребує окремого іменованого примітиму
вручну, не масштабується; (2) "naked"-функції з ручним прологом/
епілогом для обробників переривань; (3) реальні типи розміру (int8/
16/32/64, беззнакові) замість "усе - double з латками", як оце щойно
зроблена; (4) volatile/пам'ять-бар'єри для MMIO. Реалістична ціль
після поточного плану - писати 95%+ реального ядра без ручного asm,
не "asm більше не потрібен ніде".

## Фаза N11 — Справжній inline-asm (22.09.2026)

Sviatoslav's пріоритет #1 зі списку "чого бракує, щоб замінити C/
Assembler" (21-22.09.2026, зафіксовано в пам'яті
[[project-nyxilum-native-compiler]]): без цього кожна нова
привілейована/специфічна інструкція (cpuid, lgdt/lidt, rdtsc, lock
cmpxchg, rep movsb, rdmsr/wrmsr...) вимагала б окремого іменованого
компілятор-інтринзика вручну (той самий шаблон, що inb/outb/hlt) - не
масштабується.

**Реалізація** - `asm("...")`/`asm("...", "...", ...)`, kernel-target-
only, той самий "перехоплення за іменем виклику" механізм, що вже
дають peek/poke/in*/out*/hlt (жодних змін у Lexer/Parser не
знадобилось - `asm(...)` і так парситься як звичайний CallExpression з
рядковими літерал-аргументами). Кожен аргумент МАЄ бути рядковим
ЛІТЕРАЛОМ (відомим на етапі компіляції) - кожен йде в згенерований .s
ДОСЛІВНО, своїм рядком. Кілька аргументів = кілька послідовних
інструкцій.

СВІДОМО без списку "clobbers" (на відміну від GCC/Clang
`asm volatile(... : : : "clobbers")`) - компілятор не намагається
вгадати, які регістри/прапорці змінить довільний текст. Це той самий
рівень довіри, що й реальний "голий" inline-asm - мінімальна перша
версія, не хиба.

**Перевірено живцем ДВОМА способами** (freestanding C-гарнес, без
libc - `-m32 -ffreestanding -nostdlib`, той самий підхід, що для всіх
kernel-примітивів):
1. `asm("mov $42, %eax")` всередині функції - підтверджено в
   згенерованому .s, що інструкція потрапляє ДОСЛІВНО.
2. **Реальний СПОСТЕРЕЖУВАНИЙ побічний ефект**: `asm("movl $99,
   __g_marker")` записує напряму в адресу СПРАВЖНЬОЇ compiler-
   керованої глобальної змінної (`var marker: string;` -> мітка
   `__g_marker`), значення потім прочитане ЗВИЧАЙНИМ NyxilumLang-кодом
   (`return marker;`) - `harness2.c` підтвердив: до виклику `asm`-
   функції маркер == 0 (null), ПІСЛЯ == 99. Перше реальне доведення, що
   inline-asm може змінювати стан, видимий решті скомпільованої
   програми, а не просто "виконує щось ізольоване".

Регресій нуль: 67/67 (VM) - фіча повністю kernel-target-only,
жодного нового коду на VM/byte-код/Linux-шляхах.

**Чесно про залишок**: inline-asm закриває gap #1 зі списку, але НЕ
весь список. Лишається: naked-функції (ручний пролог/епілог для
обробників переривань), реальні типи розміру (int8/16/32/64,
беззнакові), volatile/пам'ять-бар'єри, справжні типізовані вказівники,
самокомпіляція.

## Висновок: мова "замінює" асемблер (не "краще за нього") - 22.09.2026

Sviatoslav's пряме уточнення: не гнатись за "краще за асемблер" зараз -
досить, щоб мова МОГЛА його замінити, своїм способом, а не копіюючи
C один-в-один - решту (per-item покращення) відкласти на потім, бо
попереду ще Anylint і (за умови, що все піде гладко) ігровий рушій.

**Чесна перевірка залишку (naked-функції/типи розміру/volatile/
типізовані вказівники) через призму "чи це РЕАЛЬНО блокує заміну":**

- **Типи розміру** - НЕ окрема мовна фіча потрібна: 1-байтовий доступ
  (`s[i] = ...`) і 4-байтовий (`peekNum`/`pokeNum`) уже існують і УЖЕ
  комбінуються для змішаних розмірів (rtc.c - `year` u16 записано
  ДВОМА байтовими записами, а не новим типом). Прагматично покрито.
- **volatile** - НЕМАЄ чого реалізовувати: цей компілятор не робить
  ЖОДНОЇ оптимізації з переупорядкуванням/кешуванням пам'яті (кожен
  вираз компілюється прямолінійно, без CSE/reordering) - volatile-
  семантика вже виконується самою відсутністю оптимізацій.
- **Реальні типізовані вказівники** - повна `ptr<T>`-система з
  дженериками - велика окрема робота; АЛЕ "адреса + peek/poke руками"
  (як kheap.c/pci.c/rtc.c уже роблять) - це ТОЙ САМИЙ рівень, на якому
  пишеться реальний low-level C-код до появи зручних абстракцій. Не
  елегантно, але ПРАЦЮЄ - заміна, не покращення.
- **"Naked"-функції** - ЄДИНИЙ пункт із реальною, а не косметичною
  межею: компілятор ЗАВЖДИ огортає функцію своїм прологом/епілогом
  (`push %ebp.../pop %ebp; ret`) - справжній ISR-трамплін потребує
  `iret`, не `ret`, і не може покладатись на звичайний стан стека
  виклику. АЛЕ - NyxOS's РЕАЛЬНА, вже робоча архітектура (isr.s) і так
  тримає ЦЕЙ конкретний, мінімальний шматок (сире збереження регістрів
  + iret) вручну написаним asm, а ВСЮ реальну логіку обробника
  (timer_handler, scheduler_tick тощо) вже викликає як звичайну
  функцію - точнісінько так само влаштовані реальні продакшн-ядра
  (напр. Linux) - тримати мікроскопічний trap-stub сирим asm, а решту
  ядра - мовою вищого рівня, все одно вважається "ядро написане на
  X", не "ядро написане на asm". Це властивість апаратних переривань
  x86, не прогалина ЦІЄЇ мови.

**Висновок**: за пріоритетом Sviatoslav'а ("замінити, не бути кращим")
- мова ПІСЛЯ Фаз N8-N11 вже РЕАЛЬНО здатна написати практично все ядро
  NyxOS без ручного asm, крім неминучого мінімального ISR-трампліна
(властивість заліза, не мови). Подальші покращення (per-item з
Фази N10/N11 "чесно про залишок") - ЯКІСТЬ/ЕРГОНОМІКА, не
"чи взагалі можливо" - свідомо відкладені. Наступний крок за
домовленістю - Anylint, потім (якщо все піде гладко) ігровий рушій.

## Фаза N12 — справжні Int32/UInt32 (22.09.2026) — ЗАВЕРШЕНО

Anylint і "заплановано - потім рушій" (обидва вище) виявились не
кінцевою точкою: Sviatoslav підняв планку ЩЕ РАЗ того самого дня -
не просто "замінити" asm, а "могла повністью замінити asm або навіть
бути краще нього". Рушій (уже спланований, затверджений) свідомо
відкладено на користь цього - див. [[project-nyxilum-engine-deferred]]
у пам'яті. Написано й затверджено окремий план ("Фаза N12+") перед
стартом, за новою стандартною вимогою [[feedback-always-plan-big-projects-first]].

**Корінна причина, чому N10/N11 - все ще "обхідні шляхи", не
фундамент**: увесь компілятор представляє ЧИСЛА як `double`
(рішення Фази N3) - `ValType.Number` пронизує 54 місця в
`NativeCodegen.cs`. N10 виправив ЛИШЕ конвертацію на межі побітових
операторів - справжнє переповнення/розмір у пам'яті/типізовані
вказівники все ще впирались у ту саму корінну причину.

**Реалізація** - додаткова, kernel-target-only система типів (той
самий принцип, що N8-N11 - НІЧОГО в double/Number-шляху чи в 67/67
VM-регресії не змінено):
- `ValType.Int32`/`ValType.UInt32` - значення живуть як сирі
  4-байтові GPR-значення, НЕ double/%xmm0.
- Нові імена анотацій `int32`/`uint32` (СВІДОМО не перевикористано
  вже наявні `i32`/`u32` - ті лишаються Number-псевдонімами, щоб не
  тихо змінити поведінку існуючого коду) - розпізнаються в глобальних
  змінних, параметрах/return-типах kernel-функцій.
- Новий `CompileIntBinary()` - арифметика напряму на GPR, БЕЗ
  жодного double round-trip. Signed vs unsigned нарешті РОЗРІЗНЯЮТЬСЯ
  там, де це реально впливає: ділення/остача (`idiv`+`cdq` vs
  `div`+`xor edx,edx`), порівняння (`setl/setg` vs `setb/seta`), і
  ГОЛОВНЕ - зсув вправо (`sar` vs `shr`) - САМЕ ця різниця була
  НЕМОЖЛИВА у Фазі N10 (double-бітовий-патерн не ніс інформації про
  знаковість - "-8 >> 1" і "0xFFFFFFF8 >> 1" виглядали ОДНАКОВО).
- `~` (унарний bitwise-not) для Int32/UInt32 - пряме `not %eax`, без
  round-trip узагалі.
- `toI32()`/`toU32()`/`toNumber()` - явні конвертери РІВНО на межі
  Number<->Int32/UInt32 ("convert once at the boundary", та сама
  дисципліна, що вже є для kernel-параметрів/numToPtr).
- Kernel-виклики (аргументи/return) розширено приймати Int32/UInt32
  так само, як String (уже 4-байтове значення).

**РЕАЛЬНИЙ БАГ, знайдений під час реалізації**: `if/else if`-ланцюжок,
що вирішує тип ГЛОБАЛЬНОЇ змінної, обчислював тип з інферованого типу
double-літерала-ІНІЦІАЛІЗАТОРА ще ДО того, як хоч раз глянути на
`v.TypeAnnotation` - `var x: int32 = 5;` мовчки типізувалась би як
звичайний Number, ігноруючи анотацію. Виправлено: анотація `int32`/
`uint32` тепер МАЄ пріоритет над інференсом із літерала.

**Перевірено живцем** (`native-examples/n12-int-types/`, freestanding
C-гарнес, `gcc -m32 -ffreestanding -nostdlib`, той самий підхід, що
всі попередні фази) - 12 окремих перевірок, усі пройдено з першого
разу ПІСЛЯ виправлення реального бага в САМОМУ гарнесі (inline-asm
register-clobber, задокументовано в `native-examples/n12-int-types/README.md`
як окремий урок): UInt32-переповнення (`0xFFFFFFFF + 1 -> 0`),
Int32-переповнення (`INT32_MAX + 1 -> INT32_MIN`), signed-ділення
(`-7 / 2 -> -3`, обрізка до нуля), unsigned-ділення того самого
бітового патерна (`0xFFFFFFFE / 2 -> 0x7FFFFFFF`, а НЕ `-1`, як було
б із `idiv`), signed/unsigned порівняння того самого `0xFFFFFFFF`
(як -1 signed - менше за 1; як 4294967295 unsigned - НЕ менше за 1),
`sar` vs `shr` на ТОМУ САМОМУ `0xFFFFFFF8` (-8 signed -> -4; unsigned
-> 0x7FFFFFFC), `~5 -> -6`, round-trip `toNumber`/`toI32`/`toU32` для
звичайного й великого (>2^31) значень, побітові на GPR без
double-конвертації. 67/67 VM-регресій без змін.

**Наступний крок за планом**: Фаза N13 (Int8/16/64, UInt8/16/64 - той
самий патерн, повторений); потім N14 (реальні типізовані вказівники
`ptr<T>`, залежить від N12/13); N15 (naked-функції - стає РЕАЛЬНО
зручним лише після N12-N14, не раніше); N16 (явний `volatile`).

## Фаза N13 — Int8/UInt8/Int16/UInt16 (22.09.2026) — ЗАВЕРШЕНО

Розширення N12-патерна на 4 нові розміри (Int64/UInt64 СВІДОМО НЕ тут
- справжня 64-бітна арифметика на 32-бітному x86 потребує software-
емуляції через пари регістрів із carry-пропагацією для +/- і
розширеним множенням/діленням - якісно інша, значно більша окрема
робота, не просто "ще одна ширина", чесно відкладена на майбутню
фазу, а не тихо пропущена).

**Рефакторинг перед розширенням**: централізовано розкидані
`== ValType.Int32 || == ValType.UInt32`-перевірки (8+ місць файлу) у
`IsSizedIntType()`/`IntTypeInfo()`/`SizedIntFromAnnotation()` - без
цього кожне з 4 нових розмірів довелось би вручну дописувати окремо
в кожне з тих місць ще раз.

**Новий центральний інваріант**: Int8/16/32-значення в %eax ЗАВЖДИ
знаково розширені, UInt8/16/32 - ЗАВЖДИ беззнаково розширені, НІКОЛИ
"сире сміття у верхніх байтах" (`EmitNarrowExtend` після кожної
операції, що МОЖЕ вивести значення за межі ширини - `+`/`-`/`*`/`<<`/
побітові; порівняння й `>>` не потребують re-truncate, доведено в
коментарі коду). Це дозволяє порівнянням (`cmp`) і арифметичному/
логічному зсуву працювати НАПРЯМУ на повному 32-бітному регістрі для
БУДЬ-ЯКОЇ ширини - без інваріанту довелось би писати окрему
"вузьку" версію кожної інструкції.

**Ділення/остача - єдине місце, що вимагає СПРАВДІ різних
інструкцій за шириною** (не просто "той самий opcode, інший розмір
операнда") - x86 не має узагальненого `div`: байтове ділення бере
дивіденд з AX (через `cbw`/zero-extend), дає частку в AL/остачу в AH;
словне - з DX:AX (`cwd`/zero-extend), частка AX/остача DX; подвійне
слово - з EDX:EAX (Фаза N12, без змін). Виділено в окремий
`EmitIntDivision()`.

**Зберігання глобальних - свідомо ОДНАКОВЕ для всіх 6 типів**
(повний 4-байтовий `.long` слот, не `.byte`/`.word`) - "ширина" типу
впливає лише на арифметику В РЕГІСТРІ, не на розмір пам'яті;
byte/word-точна пам'ять - уже наявні `peek`/`poke`-примітиви (Фаза
N8), не дублюється тут.

**Перевірено живцем** (`native-examples/n13-sized-ints/`, той самий
freestanding-гарнес підхід) - 17 окремих перевірок, усі пройдено:
переповнення на межі кожної ширини (Int8 `100+50→-106`, UInt8
`200+100→44`, Int16 `30000+10000→-25536`, UInt16 `60000+10000→4464`),
signed/unsigned ділення РІЗНОЇ ширини (`divI8`/`divU8` через byte-
ширини `idivb`/`divb`, `divI16`/`divU16` через word-ширини
`idivw`/`divw`), порівняння, `sar` vs `shr` на ТОМУ САМОМУ 16-бітному
патерні `0xFFF8`, `~` на UInt8 (перевіряє, що zero-розширення
застосовується - без нього результат хибно був би signed), `toNumber`/
`toI16`/`toU8` round-trip, множення з обгортанням за модулем ширини
(`UInt8: 200*200 mod 256 = 64`). Санітарна самоперевірка гарнеса
(підміна одного очікування на свідомо неправильне) підтвердила, що
тест РЕАЛЬНО ловить розбіжності, не проходить мовчки. Перевірено
ПОВТОРНО й старий N12-тест (12 перевірок, width=4) - усе ще 0
провалів після рефакторингу на спільні хелпери. 67/67 VM-регресій
без змін.

**Наступний крок за планом**: N14 (реальні типізовані вказівники
`ptr<T>`, залежить від N12/N13 - T нарешті має реальний сенс); N15
(naked-функції); N16 (явний `volatile`). Int64/UInt64 (частина
початкового опису N13) - окрема майбутня фаза, чесно НЕ зроблена цієї
сесії.

## Фаза N14 — справжні типізовані вказівники `ptr<T>` (22.09.2026) — ЗАВЕРШЕНО

Перша РЕАЛЬНА, хоч і навмисно вузько обмежена, зміна синтаксису мови
цим планом (не лише нова анотація-слово, як усі N12/N13) - "ptr<T>"
вимагав `<`/`>` у типовій позиції, а `ParseType()` (Parser.cs) до
цього розпізнавав ЛИШЕ одинарний keyword/identifier-токен чи `[T]`.
Додано ЄДИНИЙ спеціально розпізнаний випадок "ім'я<...>" (лише коли
ім'я типу - буквально "ptr") - НЕ повноцінні дженерики для всієї
мови, `<`/`>` тут ТІ САМІ Operator-токени, що звичайні порівняння,
лексер їх і так уже давав без змін, розпізнавання - лише за позицією.
ЖОДНОГО ризику для решти мови - зміна активується ЛИШЕ коли токен
"ptr" безпосередньо передує "<" у типовій позиції.

**Реалізація** (`NativeCodegen.cs`) - `ValType.Ptr`, ОДИН новий тег
(не по одному на кожен T, як міг би вийти наївний підхід) - тип
ЕЛЕМЕНТА зберігається "збоку" у `_ptrElementType` (локальні/
параметри, скидається щофункції) та `_globalPtrElementType`
(глобальні + return-типи kernel-функцій, персистентний, той самий
патерн, що вже дав `_varStructName` для `ValType.Struct`). Нова
`InferPtrElementType()` - дзеркало `InferExprType`, але для типу
ЕЛЕМЕНТА довільного вказівникового виразу (змінна, `ptr + N`
успадковує елемент ЛІВОГО, виклик функції з `-> ptr<T>`).

**`ptr[i]`/`ptr + N` - справжнє масштабування на `sizeof(T)`** (суть
відмінності від старої String-based "адреса + зсув руками", Фаза N8)
- `ptr[i]`: НАПРЯМУ x86-адресація `(%eax,%ecx,SCALE)` - природна
підтримка масштабів 1/2/4/8, точнісінько ширини всіх sized-int типів
і `double` - ОДНА інструкція читає/пише ЩО завгодно, замість
кількох `peekNum(ptr + i*4)`-подібних ручних кроків. `ptr + N`/
`ptr - N`: явний `imul $sizeof(T), %ecx, %ecx` (SCALE-адресація не
масштабує від'ємно для `-`, тому явний imul, а не lea-трюк).
Порівняння (`==`/`!=`) розширено на Ptr (та сама ідентичність-адрес
семантика, що String).

**Перевірено живцем** (`native-examples/n14-typed-pointers/`) - 9
перевірок: базове читання/запис `ptr<int32>`/`ptr<uint8>`/
`ptr<int16>`, і КЛЮЧОВИЙ доказ реального масштабування - та сама пара
buf[0]+buf[1] прочитана через `ptr<int32>` (масштаб 4) ПРОТИ
`ptr<uint8>` (масштаб 1) дає РІЗНУ адресну арифметику для "p+1", обидві
перевірені окремо з різними очікуваними сумами. Санітарна самоперевірка
підтвердила, що тест реально ловить розбіжності. Регресія: старі N12/
N13-тести (21 перевірка) повторно пройдено ПІСЛЯ зміни спільного
`Parser.cs` - 0 провалів; 67/67 VM-тестів (Parser.cs зачіпає ВСІ цілі,
не лише kernel) - без змін.

**Свідомо поза обсягом**: вкладені вказівники (`ptr<ptr<T>>`),
String/Bool як елемент T, `sizeof()`-вираз мовою (розмір рахує лише
компілятор внутрішньо) - чесна помилка компіляції для будь-якого з
цього, не мовчазна хибна поведінка.

**Наступний крок за планом**: N15 (naked-функції - стає РЕАЛЬНО
зручним лише тепер, коли є і точні цілі типи, і типізовані вказівники);
N16 (явний `volatile`).
