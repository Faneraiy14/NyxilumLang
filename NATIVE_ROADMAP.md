# План: справжня нативна компіляція NyxilumLang (x86, без VM під час виконання)

Мета Sviatoslav'а (14.09.2026): після того, як NyxilumLang зможе
компілюватись у СПРАВЖНІЙ машинний код (не в байткод для VM, яка сама
потребує повноцінної ОС/.NET під собою) — переписати ядро NyxOS (чи
його частини) цією ж мовою, а згодом і написати власний BIOS.

**Чесно про масштаб:** це НЕ "додати ще одну команду `nx build --native`"
— це фактично НОВИЙ компілятор-бекенд, порівнянний за обсягом роботи з
усім NyxOS. Причина: `VirtualMachine.cs` (1440 рядків) покладається на
CLR буквально в усьому — значення (`object`, боксовані double/string/
структури), змінні (`Dictionary<int, object>` на кадр, НЕ реальні
слоти стека), виклики функцій (керовані `Stack<>`, MaxCallDepth=10000,
НЕ справжній `call`/`ret`), замикання (CLR-делегати/мапи), винятки
(`throw`/`try` самого C#), збирання сміття (сама CLR). Нативний
компілятор мусить переізобрести КОЖНУ з цих речей руками на голому x86
— саме тому обрано найважчий, "справжній" шлях (за явним вибором
Sviatoslav'а, а не легший байткод-у-VM-в-ядрі варіант).

**Стратегія:** будувати native-бекенд ОКРЕМО від NyxOS, спершу під
ЗВИЧАЙНУ Linux (де є gdb, можна порівняти вивід з VM напряму) — і лише
ПІСЛЯ того, як він стабільно працює на нормальній ОС, переносити на
freestanding NyxOS. Змішувати "чи взагалі генерується правильний x86" і
"чи працює це без ОС під собою" одночасно — рецепт заплутатись і не
відрізнити один клас багів від іншого.

## Фаза N1 — Найменший можливий реальний зріз (доказ, що ідея працює) ✅ ЗАВЕРШЕНО (14.09.2026)

**Зроблено й перевірено живцем** (`src/NyxilumLang/Native/NativeCodegen.cs`,
команда `nx compile-native <file.nx> [-o out]`): цілі числа, `+ - * / %`,
`var`, `print()` - СПРАВЖНІЙ 32-бітний статично злінкований ELF, вивід
побайтово звірено з існуючою VM. 2 реальні баги знайдено й виправлено
(print() - окремий вузол AST PrintStatement, не CallExpression).

1. **Мінімальний підмножина мови**: цілі числа, `+ - * /`, `var`,
   `print()`, ОДНА функція `main()` без параметрів. Жодних if/while/
   функцій/масивів/структур ще.
2. **Codegen у GAS-асемблер (AT&T)**: той самий інструмент (`as`/`ld`),
   що вже використовується в NyxOS — НЕ винаходити свій асемблер,
   компілятор генерує ТЕКСТ `.s`-файлу, `as`+`ld` роблять решту.
3. **Ціль - Linux x86-32, БЕЗ libc** (сирі syscall'и через `int 0x80` -
   НЕ через `printf`, ближче до того, що знадобиться на NyxOS) - `print()`
   через `printf`/`write` сисколл напряму, простіше налагоджувати
   (можна `gdb`, `objdump -d`, порівняти з `gcc -S` для контрольного
   прикладу).
4. **Живий тест**: скомпілювати `var a = 2 + 2 print(a)`, зібрати в
   реальний ELF, ЗАПУСТИТИ, побачити "4" в терміналі. Порівняти з
   виводом ТОГО САМОГО файлу через існуючий `nx run`.

`continue` (стек активних міток циклу, вкладені цикли), присвоєння

літерали тихо обрізались до цілого замість чесної помилки).

5. `if`/`else`, `while`, `break`/`continue` (прямий переклад у
   `cmp`+`jCC` - НАБАГАТО простіше, ніж VM-байткод, бо немає стека

6. Кілька функцій, реальні `call`/`ret` зі СПРАВЖНІМ стеком викликів
   (на відміну від VM - тут native-стек ОС сам дає рекурсію "безкоштовно",
   без штучного MaxCallDepth).
7. Локальні змінні як реальні слоти на стеку (offset від EBP/RBP,
   вирахувані НА ЕТАПІ КОМПІЛЯЦІЇ) - не Dictionary, як у VM.

## Фаза N3 — Значення й типи

8. **Представлення значень** ✅ ЧАСТКОВО ЗАВЕРШЕНО (14.09.2026, дробові
   числа). Замість повного tagged union/NaN-boxing (значно більший
   крок, і далі відкладений) - обрано СТАТИЧНИЙ (не рантайм) тип на
   рівні компілятора: `InferExprType()` визначає для КОЖНОГО виразу
   Number чи Bool ще на етапі компіляції, і компілятор генерує РІЗНІ
   інструкції/регістри залежно від типу (Number -> SSE2/%xmm0 -
   справжній 8-байтовий double, той самий формат, що вже дає
   Parser.cs; Bool -> %eax, як і в Фазі N1-N2). Це можливо, бо мова
   зараз не дозволяє змінній міняти тип у рантаймі динамічно так, щоб
   компілятор не міг вивести його статично - якщо це колись
   знадобиться, доведеться повертатись до повноцінного tagged union.
   Живцем перевірено: дробова арифметика (+ - * / %, останній - через
   trunc(a/b)-формулу), порівняння (ucomisd), унарний мінус, `print()`
   чисел (власний print_double - конвертує double в десятковий ASCII
   вручну, БЕЗ printf/libc) і bool (текстом "True"/"False" - РЕАЛЬНА
   розбіжність, знайдена звіркою з VM: VM друкує через C#-типове
   object.ToString(), яке дає "True", не "true"). **ВІДОМЕ,
   задокументоване обмеження**: print_double НЕ дає короткий
   round-trip запис для дробів без точного двійкового представлення
   (напр. 3.5/1.25 = 2.8 у VM, але "2.799999999999999" у native -
   потребує Grisu/Ryu-подібний алгоритм, окрема майбутня задача) - для
   рівно-двійкових дробів (3.5, 1.25, 4.75 і т.п.) збігається
   ПОБАЙТОВО. Функції поки повертають лише Number (bool-результат -
   тільки для return у main(), як код виходу). NyxOS-ціль
   (--target nyxos) і далі успішно асемблюється/лінкується з цим
   кодом (структурна перевірка), повний живий тест УСЕРЕДИНІ NyxOS
   для дробових чисел - ще не зроблено (наступний крок).
9. Рядки, масиви, структури - усі як вказівники на купу ✅ ЧАСТКОВО
   ЗАВЕРШЕНО (14.09.2026, рядки + масиви). Замість malloc/free з libc
   (як спершу пропонував цей пункт) - ВЛАСНИЙ, написаний ВРУЧНУ
   bump-розподілювач (`heap_alloc`, EmitHeapAllocHelper) через syscall
   brk (#45) - рішення змінено НА КРАЩЕ під час реалізації: компілятор
   і так свідомо НІДЕ не лінкується з libc (сирі syscall'и всюди,
   ближче до freestanding NyxOS), тож підключати libc ЛИШЕ заради
   malloc означало б тягнути динамічний лінкер (PLT/GOT, interpreter
   path) - значно складніша, окрема ІНЖЕНЕРНА тема, ніж написати
   40-рядковий bump-аллокатор самому. Немає free()/GC - пам'ять
   "тече", чесно, як і планувалось тут же нижче.

   **Рядки** (`ValType.String`, вказівник-eax): статичні .rodata-
   літерали, присвоєння/перевизначення змінній, print() (з рантайм
   strlen для Linux - довжина більше НЕ завжди відома на етапі
   компіляції, бо змінна могла вказувати на РІЗНІ рядки). Стара
   спецгілка прямого `print("...")` УНІФІКОВАНА із загальним шляхом
   (одна логіка для літералу й змінної, перевірено побайтово - вивід
   не змінився). Арифметика/порівняння над рядками (навіть ==/!=) -
   явна помилка компіляції: content-порівняння (strcmp) ще не
   реалізовано, і незрозуміло, чи identity-порівняння (просто адреси)
   збіглось би з тим, як порівнює рядки VM - чесна відмова краща за
   неперевірену поведінку.

   **Масиви** (`ValType.Array`, вказівник-eax): `[довжина:4][padding:
   4][елементи по 8 байтів]`. СПРОЩЕННЯ - лише Number-елементи (немає
   tagged union для змішаних типів). Літерал `[1,2,3]`, читання
   `arr[i]`, запис `arr[i] = x` - усе живцем перевірено проти VM,
   побайтовий збіг (включно з накопиченням суми в циклі). БЕЗ
   перевірки меж (вихід за межі читає/пише поза блоком) - відоме,
   свідомо не виправлене обмеження. print(масив) напряму, арифметика/
   порівняння над САМИМ масивом - явна помилка (індексуйте arr[i]).

   **Ціль --target nyxos**: рядки й масиви поки працюють ЛИШЕ для
   --target linux - у ABI NyxOS ще немає syscall'у виділення пам'яті
   (потрібного для heap_alloc) - чесна помилка компіляції замість
   мовчазної поломки на реальній NyxOS. Живий тест УСЕРЕДИНІ NyxOS - і
   для дробових чисел (попередній пункт), і для рядків/масивів -
   лишається окремим наступним кроком (Фаза N6).

   **Структури** ✅ ЗАВЕРШЕНО, ЛИШЕ ПОЛЯ (14.09.2026). `var p =
   Struct { field: value, ... }`, читання/запис `p.field` - живцем
   перевірено проти VM, побайтовий збіг. Offset полів обчислюється
   ОДИН РАЗ на весь файл (структури - верхній рівень, не всередині
   функцій). СПРОЩЕННЯ: лише Number-поля, ВСІ поля - явно (без
   значень за замовчуванням). Методи (func Struct.method - функція з
   неявним self) і успадкування (extends/super) - СВІДОМО НЕ
   реалізовано цим бекендом (чесна помилка компіляції при спробі) -
   суттєво більший обсяг, ніж самі поля, і по суті вже НАЛЕЖИТЬ Фазі
   N4 (методи/виклики - близькі до замикань за складністю диспетчеризації).
10. `==`/`!=` з тим самим правилом, що вже задокументовано в
    tests/test_equality.nx (2 == 2.0 - true, порівняння за ЗНАЧЕННЯМ,
    не за "коробкою").

## Фаза N4 — Замикання, винятки, збирання сміття

10.5. **Методи структур** ✅ ЗАВЕРШЕНО (15.09.2026) - `obj.method(args)`,
    неявний `self` (перший параметр - той самий підхід, що вже дає
    Parser.cs: self - звичайний FunctionParameter із Type=ім'я
    структури). Кожен метод - під унікальною міткою
    "StructName__methodName". РЕАЛЬНИЙ баг, знайдений живим тестом:
    Parser.cs зберігає ПОВНЕ ім'я методу як "StructName.methodName" у
    FunctionDeclaration.Name - перша версія шукала за "голим" іменем і
    завжди провалювалась. Живцем перевірено проти VM - побайтовий
    збіг. СПРОЩЕННЯ: аргументи/поля/повернення - лише Number, лише
    --target linux (як і структури взагалі).

11. Замикання (`var f = func(){...}`) ✅ ЗАВЕРШЕНО, ЗІ СПРОЩЕННЯМ
    (15.09.2026) - без CLR-делегатів: явна структура "вказівник на код
    + вказівник на захоплене оточення" (той самий підхід, що C++
    лямбди компілюються в machine code). Живцем ЗВІРЕНО з VM (не
    здогадка!) - `tests/test_closures.nx` явно показав, що захоплення
    в НАЯВНІЙ VM - ЗА ЗНАЧЕННЯМ (знімок на момент створення), а НЕ за
    посиланням, як спершу читалось з селфхост-інтерпретатора (окрема,
    ІНША реалізація мови, не той самий VirtualMachine.cs) - власний
    тест підтвердив ще й, що мутація ВСЕРЕДИНІ тіла НЕ зберігається
    між викликами того самого замикання. Реалізовано як "копія в
    env-блок на купі при СТВОРЕННІ + копія з env у ЗВИЧАЙНІ локальні
    слоти на ПОЧАТКУ КОЖНОГО виклику" - жодної непрямої адресації при
    читанні/записі всередині тіла не треба (захоплена змінна - просто
    ще один локальний слот). 2 РЕАЛЬНІ баги знайдено й виправлено:
    (1) env-вказівник при виклику передавався звичайним 4-байтовим
    `push` замість уніфікованого 8-байтового слота - зсувало ВСІ інші
    параметри; (2) вкладена лямбда, якій потрібна змінна з
    "дідівської" (не безпосередньо охоплюючої) області - виявлення
    вільних змінних не поширювало захоплення транзитивно, виправлено
    стандартним closure-conversion підходом. СПРОЩЕННЯ: замикання -
    лише як локальна змінна (створити й викликати), НЕ як аргумент
    функції й НЕ як return зі звичайної функції (знадобився б
    статичний вивід типу РЕЗУЛЬТАТУ довільного виклику, а не
    універсальне "усі функції - Number"); захоплювати можна лише
    Number-змінні; лише --target linux (потрібен heap_alloc).
12. `try`/`catch`/`throw` - БЕЗ CLR exceptions: `setjmp`/`longjmp`-
    стиль (той самий трюк, що вже реалізовано в NyxOS - `context_save`/
    `context_restore`, gdt_asm.s) - стек активних `try`-блоків, кожен
    зберігає точку повернення.
13. Збирання сміття - НАЙЧЕСНІШЕ: почати БЕЗ нього (просто "текти" -
    прийнятно для коротких/скриптових програм), справжній GC (mark-
    sweep чи проста лічба посилань) - окремий, значний майбутній крок,
    не блокує решту плану.
