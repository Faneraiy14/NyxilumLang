# Фаза N13 - Int8/UInt8/Int16/UInt16 (живий тест)

Той самий підхід, що `n12-int-types/` - freestanding `gcc -m32
-ffreestanding -nostdlib` C-гарнес, без libc, без NyxOS.

## Файли

- **`n13_test.nx`** - 17 kernel-функцій/перевірок: переповнення на межі
  ширини (Int8/UInt8/Int16/UInt16), signed/unsigned ділення РІЗНОЇ
  ширини (byte-ширини `idivb`/`divb`, word-ширини `idivw`/`divw`),
  порівняння, зсуви (`sar` vs `shr` на тому самому 16-бітному
  патерні), `~` з обов'язковим zero-розширенням для unsigned, `toI8`/
  `toU8`/`toI16`/`toNumber` round-trip, множення з обгортанням за
  модулем ширини типу (`200 * 200 mod 256 = 64`).
- **`harness.c`** - той самий шаблон, що n12-int-types (включно з
  уроком про `_exit_` - виправлено тут одразу з явними регістровими
  обмеженнями `"a"(1), "b"(code)`, а не ручним `mov`, щоб не повторити
  той самий баг).

## Як перевірити самостійно

```bash
nx compile-native n13_test.nx -o n13_test --target nyxos-kernel
gcc -m32 -std=gnu11 -ffreestanding -nostdlib -fno-stack-protector -c harness.c -o harness.o
ld -m elf_i386 -e _start harness.o n13_test.o -o n13run
./n13run; echo "fail_mask: $?"   # 0 = усі 17 перевірок пройшли
```

Перевірено (санітарна перевірка на саму себе): підміна одного
очікуваного значення в `harness.c` на свідомо неправильне дає ненульовий
exit-код - тест реально виявляє розбіжності, не проходить мовчки.

## Свідоме архітектурне рішення - однакова ширина ЗБЕРІГАННЯ

Int8/16/UInt8/16 (як і Int32/UInt32 з Фази N12) зберігаються в
пам'яті (глобальні змінні) як ОДНАКОВИЙ повний 4-байтовий `.long`
слот - "ширина" типу впливає ЛИШЕ на арифметику/обрізку значення В
РЕГІСТРІ (`CompileIntBinary`/`EmitNarrowExtend`), а НЕ на розмір
пам'яті. Byte/word-точна ПАМ'ЯТЬ - це вже наявні `peek`/`poke`-
примітиви (Фаза N8) з ручним маскуванням - не дублюється тут ще раз.
