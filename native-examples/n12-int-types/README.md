# Фаза N12 - справжні Int32/UInt32 (живий тест)

Freestanding-перевірка `ValType.Int32`/`ValType.UInt32` у
`NativeCodegen.cs` (--target nyxos-kernel) - той самий підхід, що для
всіх попередніх kernel-примітивів (`gcc -m32 -ffreestanding -nostdlib`,
без libc, БЕЗ NyxOS - лише арифметика, не привілейовані інструкції).

## Файли

- **`n12_test.nx`** - 12 kernel-функцій, кожна - окрема перевірка:
  переповнення (signed/unsigned), ділення/остача, порівняння, зсуви
  (`sar` vs `shr` на ТОМУ САМОМУ бітовому патерні), `~`, `toI32`/
  `toU32`/`toNumber` round-trip, побітові без double round-trip.
- **`harness.c`** - викликає кожну функцію через C ABI, звіряє з
  еталонним C-обчисленням, встановлює один біт у `fail_mask` за кожну
  розбіжність. Exit-код процесу = `fail_mask` (0 = усі 12 пройшли).

## Як перевірити самостійно

```bash
nx compile-native n12_test.nx -o n12_test --target nyxos-kernel
gcc -m32 -std=gnu11 -ffreestanding -nostdlib -fno-stack-protector -c harness.c -o harness.o
ld -m elf_i386 -e _start harness.o n12_test.o -o n12run
./n12run; echo "fail_mask: $?"   # 0 = усі перевірки пройшли
```

## Реальний баг, знайдений і виправлений ПІД ЧАС написання цього тесту

Перша версія `harness.c`'s `_exit_()` вручну писала
`"mov $1, %eax" / "mov %0, %ebx"` усередині `asm volatile` з
обмеженням `"r"(code)` - GCC сам обрав РІВНО `%eax` для розміщення
`code` (задоволення обмеження `%0`), а наступний рядок `mov $1, %eax`
ЗАТИРАВ це значення ще ДО того, як `mov %0, %ebx` встиг його
прочитати - функція мовчки завжди повертала `exit(1)`, незалежно від
реального `code`. Це змусило ПЕРШИЙ прогін тесту показати
`fail_mask=1` (виглядало як провал переповнення UInt32) - підтверджено
ІЗОЛЬОВАНИМ дебаг-тестом (`objdump -d`, прямий виклик лише `addU32`),
що згенерований NyxilumLang-код був насправді коректний із самого
початку. Виправлено явними регістровими обмеженнями
(`"a"(1), "b"(code)` замість ручного `mov`) - після фіксу всі 12
перевірок пройшли з першого разу.

**Урок**: баг у тестовому гарнесі виглядає ІДЕНТИЧНО бага в
компільованому коді (обидва дають "неправильний" результат) -
ізольований дебаг-тест (одна функція, один виклик, `objdump`
підтвердження) - обов'язковий крок ПЕРЕД тим, як звинувачувати сам
компілятор.
