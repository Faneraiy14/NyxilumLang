# План: NyxilumLang до рівня C → своя JVM → свій LWJGL → Voxelin на своєму

Записано 05.11.2026 за рішенням Святослава: **спершу мова, потім на ній JVM**, далі (якщо
захочеться) свій замінник LWJGL і Voxelin на всьому своєму — **окремий проєкт-експеримент**.
Основний Voxelin лишається на Java 21 + LWJGL, поки експеримент не дожене його (тоді, можливо,
стане основою). Мета всього ланцюжка — нуль сторонніх частин у тому, що запускається.

```
NyxilumLang «як C» (цей файл, етапи S1–S10)
  └─ NyxVM — JVM на NyxilumLang: байткод Java 21, своя бібліотека в обсязі Voxelin
       └─ свій «LWJGL»: вікно, ввід, OpenGL, звук — на NyxilumLang
            └─ Voxelin-експеримент: гра на всьому своєму (окремий репозиторій)
```

## Де мова зараз (05.11.2026)

Є з чого починати, але для JVM бракує головного.

| Є | Немає (для JVM критично) |
|---|---|
| Нативний x86 **32-біт** (`--target linux/nyxos/nyxos-kernel`): статичні типи, int8–32/uint8–32, `ptr<T>`, адреса функції й непрямий виклик, inline asm, naked, volatile, peek/poke | **64 біти**: ні x86-64, ні int64/uint64 (Java `long` — скрізь) |
| Нативний ARM64: динамічні значення (NaN-boxing), рядки/масиви/мапи/замикання | **Збирач сміття** в нативному коді (зараз лише bump-купа без free) |
| 8 модулів ядра NyxOS переписано з C | **Потоки, атоміки, futex** |
| VM на .NET, 166 вбудованих функцій | **Компілятор сам на собі**: зараз компілятор — C# (.NET), асемблер і лінкер — GNU `as`/`ld` |
| | Структури з точною розміткою (поля різного розміру, без вирівнювання на 8), union/bit-cast double↔int64 |
| | Windows (PE-файли, виклик kernel32 — на Windows без DLL системних викликів немає) |
| | Розподіл регістрів / хоч якісь оптимізації — інтерпретатор JVM на повільному коді буде повільним удвічі-втричі |

**Ключове рішення:** для системного коду — **статичний режим «як C»** (як N3–N16 на x86), а не
динамічні значення ARM64. JVM не може дозволити собі боксування кожного числа. Динамічний режим
лишається для скриптів.

## Етапи

Кожен етап закінчується перевіркою, яку можна запустити. Головна дисципліна — **порівняння**:
та сама програма на C (gcc) і на NyxilumLang дає побайтово той самий вивід.

### S1. Бекенд x86-64 (статичний режим) — ✅ ЗРОБЛЕНО 05.11.2026 (за один день, а не 3–5 тижнів)

**Що вийшло.** `nx compile-native f.nx --target linux-x64` (або `--obj` — лише `.o` без `_start`
для зшивки з C). Код: `src/NyxilumLang/Native/NativeCodegenX64.cs`, прелюдія на самій мові —
`Native/X64Prelude.nx` (друк чисел і рядків, `alloc` через mmap). Без libc і без VM.

Мова системного режиму (коротко):
```
struct Node {            // розмітка полів як у C: tag@0, value@8, next@16, sizeof 24
    tag: uint8
    value: int64
    next: ptr<Node>
    func Node.sum() -> int64 { ... self.value ... }
}
var counter: int32 = 100                     // глобальні - лише сталі
func fill(p: ptr<int32>, n: int64) {         // параметр без типу = int64
    for i in 0..n { p[i] = int32(i * i) }    // змішувати цілі типи - лише явно
}
func main() -> int32 {                       // результат main = код виходу
    var arr: ptr<int32> = alloc(10 * sizeof(int32))
    var n = new(Node)                        // ptr<Node>, нулі
    var px = Pixel { r: 255, g: 1 }          // теж ptr<Pixel>
    var buf = stackbuf(64)                   // 64 байти в кадрі функції
    var raw: ptr<uint8> = asptr(px)          // вказівник іншого типу - лише явно
    var r = syscall(1, 1, buf, 3)            // будь-який системний виклик
    print(callptr(funcaddr(fill2), 21))      // адреса функції й непрямий виклик
    return 0
}
```
Типи: int8–int64, uint8–uint64, float64, bool, ptr<T>, ptr<void>, структури. Ціле в регістрі
завжди «канонічне» (розширене до 64 біт). Операція — у межах свого типу (uint8 + uint8 переповнюється
як uint8). Виклики — System V AMD64 (до 6 цілих і 8 дробових аргументів). Ще: float64Bits /
bitsToFloat64, asm("..."), put (друк без нового рядка).

**Перевірка** (`tests/systems/run_systems.sh`, крок у CI):
- програми з еталонним виводом і кодом виходу;
- зшивка з C через --obj + gcc: розмітка структури, sizeof, змішані цілі/дробові аргументи, масив з C,
  ділення (знайшла справжню помилку: C лишає «сміття» у старших бітах вузьких цілих - тепер
  параметри канонізуються на вході);
- `gen_arith.py`: 8 цілих типів × 16 операторів × граничні значення — **42 544 результати побайтово
  як у gcc**;
- помилки типів - зрозумілі повідомлення (5 негативних тестів).
- Швидкість: fib(35) — 0.19 с проти 0.10 с у gcc -O0 і 0.03 с у gcc -O2 (регістри — етап S5).

**Свідомо не в S1:** замикання, try/catch, рядки як значення, масиви-літерали, import
(це динамічні можливості - для системного коду не потрібні або йдуть пізніше); int64 MIN / -1,
насичення float→int як у Java і точний друк дробових (S2); free (S3); виклик функцій C з
NyxilumLang (extern - разом із S10).

<details><summary>Початковий план S1</summary>

- Новий `NativeCodegenX64` на спільному `NativeFrontend`: System V AMD64 (регістри rdi/rsi/…,
  стек вирівняний на 16), `syscall` замість `int 0x80`, вказівники 8 байтів.
- Усе, що вже вміє x86-32: числа, рядки, масиви, структури, замикання, try/catch, sized-int, `ptr<T>`, asm.
- **Перевірка:** усі `tests/native` дають той самий вивід, що VM і x86-32; модулі з
  `native-examples/` компілюються під x86-64.
</details>

### S2. Числа як у Java, float32, точний друк — ✅ ЗРОБЛЕНО 05.11.2026

- **Як у Java:** `int64 MIN / -1 = MIN`, `MIN % -1 = 0`; дробове → ціле з насиченням (NaN → 0,
  за межами — межа типу; `uintN` — до [0, max]); `%` для дробових — точний fmod через x87 `fprem`.
- **float32**: тип, арифметика, порівняння, перетворення в усі боки, `float32Bits`/`bitsToFloat32`.
- **Області видимості блоків** як у C/Java: змінна живе до кінця свого `{ }` (та сама назва з іншим
  типом в іншому циклі — можна).
- **Точний друк дробових** (Burger & Dybvig на великих числах по основі 10^7, на стеку, без купи —
  написано на самій мові в X64Prelude.nx): найкоротший запис, що читається назад у те саме число,
  при рівності — парна цифра; формат як у VM (1E+20, 1E-05).
- **Перевірка:** `gen_java.py` — та сама програма на справжній Java 21 і на NyxilumLang, біти результатів
  (ділення, d2i/d2l/f2i/f2l, %, float32, зсуви включно з >>>) — **64 686 збігів**; `gen_float.py` —
  друк проти Python: випадкові біти будь-яких float64/float32, субнормальні, межі — **44 904 збіги**.
- **Знахідка:** VM (C#) друкує точні степені двійки неправильно — запис читається як ІНШЕ число
  (2^-25 → 2.980232238769531E-08 замість 2.9802322387695312E-08). Тому еталон друку — Python, а не VM.
  VM ще не виправлено.
- Ділення на 0 лишається апаратним падінням (SIGFPE): інтерпретатор JVM і так перевіряє нуль сам
  (Java кидає ArithmeticException).

<details><summary>Початковий план S2</summary>

- `int64`/`uint64` нативно (на x86-64 — просто 64-бітні регістри, без програмної арифметики).
- Java-семантика окремо від C: зсуви беруть лише 5/6 біт лічильника, ділення `MIN/-1` не падає,
  перетворення double→int насичується. Бітове перетворення `bits(double) → int64` і назад.
- **Перевірка:** таблиця граничних випадків (переповнення, ділення, зсуви, NaN→int) збігається з
  виводом невеликої Java-програми.
</details>

### S3. Пам'ять як у C — ✅ ЗРОБЛЕНО 05.11.2026

- **free / realloc**: розподілювач на самій мові (X64Prelude.nx) - 12 класів розмірів 32 Б..64 КБ зі
  списками вільних блоків, більше - окремий mmap/munmap. `alloc` завжди дає нулі.
- **memcpy / memmove / memset** (перекриття дозволене) - вбудовані, через `rep movsb/stosb`.
- **Структури в структурах і масиви в полях** (`pos: Vec3`, `name: [uint8; 13]`, `tail: [Inner; 2]`) -
  розмітка як у C; `p.pos`, `p.name`, `arr[i]` для масиву структур дають вказівник на це місце.
- **Масиви й структури на стеку**: `var buf: [uint8; 64]`, `var v: Vec3` (нулі, живуть до кінця функції).
- **addr(x)** - адреса змінної, поля чи елемента; **offsetof(S, поле)**.
- Парсер: `[T; N]` у типах і `ptr<ptr<T>>` (раніше `>>` читалось як зсув).
- **Перевірка:** розмітка складних структур (вкладені, масиви, bool, вирівнювання) і запис/читання
  в обидва боки проти C; стрес-тест: 2 млн alloc/free випадкових розмірів до 200 КБ з перевіркою
  вмісту - 0 пошкоджень, 0.79 с, процес тримає ~2.5 МБ (звільнене справді перевикористовується).
- Не зроблено (не потрібно для JVM зараз): union, enum, const, packed-структури, арени
  (арену легко написати самою мовою поверх alloc).

<details><summary>Початковий план S3</summary>

- `struct` з точною розміткою (`uint8` поле = 1 байт; `packed`/`align(N)`), `sizeof`/`offsetof`,
  `union`, масиви фіксованої довжини всередині структур, вказівник на поле.
- Свій розподілювач через `mmap` (malloc/free зі списками вільних блоків — на самій мові), арени.
- `const`, `enum`, inline-функції (константи й дрібні функції без ціни виклику).
- **Перевірка:** структура, записана з C, читається з NyxilumLang побайтово (і навпаки);
  стрес-тест розподілювача: мільйони alloc/free без росту пам'яті.
</details>

### S4. Диспетчер для інтерпретатора — ✅ ЗРОБЛЕНО 05.11.2026 (швидкість «×1.5 від -O2» - разом із S5)

- Ланцюжок `if x == 1 {..} else if x == 2 {..} ... else {..}` по одній цілій змінній і сталих
  (від 4 гілок, щільний діапазон) компілюється в **таблицю переходів**, як switch у C. Синтаксис мови
  той самий - стара VM розуміє ті самі програми. Таблиці адрес функцій уже були (funcaddr/callptr).
- **Заміри** (міні-інтерпретатор байткоду, 30 млн ітерацій, tests/systems/08_interp.nx):
  без таблиці 9.33 с → з таблицею **4.16 с**; C `gcc -O0` 4.46 с; `gcc -O2` 1.13 с.
  Тобто вже швидше за C без оптимізацій, але в 3.7 раза повільніше за -O2: решта - змінні в
  регістрах замість стека (S5).
- Тести: 08_interp (інтерпретатор), 09_switch (від'ємні, беззнакові 64-біт, пропуски, без else).

<details><summary>Початковий план S4</summary>

- `switch` по цілих → таблиця переходів (jump table), а не ланцюжок `if`.
- Масив адрес функцій/міток для «threaded code» (аналог computed goto в gcc).
- **Перевірка:** міні-інтерпретатор на 50 інструкцій: швидкість у межах ×1.5 від того самого на C `-O2`.
</details>

### S5. Розподіл регістрів і прості оптимізації — 🟡 ПЕРША ЧАСТИНА 05.11.2026

Зроблено:
- **Змінні в регістрах**: до 5 найчастіших (з вагою циклів) цілих/bool/ptr змінних функції живуть у
  rbx, r12–r15 (виклики їх не псують); змінні з `addr(x)` - у пам'яті.
- **Простий операнд без стека**: стала чи змінна праворуч (`i + 1`, `a < n`, `p[i]`, `p[i] = x`) -
  одразу в регістр, без push/pop.
- **Умови if/while** - одразу умовний перехід (`cmp; jge`), без 0/1 у регістрі; `&&` - ланцюжок
  переходів; `while true` - без перевірки.

Заміри (те саме на C - для порівняння):
| | до S5 | після | gcc -O0 | gcc -O2 |
|---|---|---|---|---|
| інтерпретатор байткоду (30 млн) | 4.16 с | **2.19 с** | 4.46 с | 1.13 с |
| fib(35) | 0.19 с | **0.11 с** | 0.10 с | 0.03 с |
| 2 млн alloc/free | 0.79 с | **0.58 с** | — | — |

Інтерпретатор - у межах ×2 від -O2 (ціль S5 для нього досягнута). Далі (друга частина S5, коли
знадобиться): проміжні значення виразів у регістрах замість стека, дробові змінні в xmm,
вбудовування дрібних функцій.

<details><summary>Початковий план S5</summary>

- Локальні змінні в регістрах (лінійне сканування), згортання констант, прибирання зайвих
  load/store, вбудовування дрібних функцій.
- **Перевірка:** набір бенчмарків (fib, сортування, міні-інтерпретатор із S4) — у межах ×2 від `gcc -O2`.
</details>

### S6. Потоки — ✅ ЗРОБЛЕНО 05.11.2026

- `spawn(funcaddr(f), arg) -> ptr<Thread>` - `clone` зі спільною пам'яттю, свій стек 1 МБ (mmap);
  `join(t) -> int64` - чекає на futex (ядро обнуляє tid при виході), звільняє стек, повертає f(arg).
- Атомарні вбудовані: `atomicAdd` (lock xadd), `atomicCas` (lock cmpxchg, повертає старе),
  `atomicSwap`, `atomicLoad`, `atomicStore` (xchg), `fence` (mfence), `cpuPause`; для
  ptr<цілого 8–64>, bool, вказівників.
- `Mutex` (lock/unlock/tryLock, futex за Дреппером: 0/1/2) і `Cond` (wait/signal/broadcast) -
  написані на самій мові в прелюдії.
- `tls()` - пам'ять цього потоку (fs → блок 4 КБ; головний потік отримує блок у `_start`).
  `threadId()` - gettid. Програма завершується `exit_group` (усі потоки).
- alloc/free безпечні для потоків: замок вмикається лише після першого spawn (без потоків - без ціни).
- **Перевірка:** tests/systems/10_threads - 8×1 млн атомарних = 8 000 000, м'ютекс 8×200 тис.,
  tls, cond+broadcast, alloc з 8 потоків. **1000 запусків поспіль - 0 збоїв, 0 зависань.**
- Обмеження: print з кількох потоків може перемішуватись (write без буфера); потоки й tls() - лише
  в самостійних програмах (не в --obj для C).

### S7. Системні двері: файли, час, мережа — 2 тижні

### S8. Самохостинг компілятора — 2–3 місяці (найбільший етап)
- Компілятор NyxilumLang, переписаний на NyxilumLang (статичний режим), що видає x86-64.
- Свій асемблер (машинний код напряму, без GNU `as`) і запис ELF (без `ld`).
- Розкрутка: C#-компілятор збирає Nx-компілятор (стадія 1) → він збирає себе (стадія 2) → ще раз
  (стадія 3). **Перевірка:** стадія 2 і стадія 3 — побайтово однакові файли. Після цього .NET і
  GNU binutils для нативного шляху більше не потрібні.

### S9. Windows — 3–4 тижні
- Запис PE-файлів, таблиця імпорту kernel32/user32 (на Windows системні виклики лише через DLL),
  Win64 ABI (rcx/rdx/r8/r9, тіньовий простір 32 байти).
- **Перевірка:** ті самі `tests/native` на Windows у CI.

### S10. Виклик чужих бібліотек ОС (лише для графіки) — 2 тижні
- Завантаження .so/.dll під час роботи (свій мінімальний завантажувач або dlopen-аналог) і
  виклики за C ABI. Потрібно ЛИШЕ для драйвера відеокарти: OpenGL живе в libGL / opengl32.dll —
  це частина ОС і драйвера, а не стороння бібліотека для гри.
- **Перевірка:** вікно X11 / Win32 з кольоровим трикутником через OpenGL.

**Сумарно до старту JVM:** S1–S7 (~4–5 місяців) достатньо, щоб почати NyxVM. S8 можна робити
паралельно з першими етапами JVM — вона ж і буде великим реальним тестом мови.

## Далі: NyxVM (коротко; деталі — у її репозиторії, коли з'явиться)

8. Пізніше: JIT.

## Далі: свій «LWJGL» і Voxelin-експеримент

- Вікно й ввід: X11 (Linux), Win32 (Windows); OpenGL 3.3 через S10; звук (ALSA / WASAPI).
- Перші збірки Voxelin на своєму — **snapshot** (`type: "snapshot"` у versions.json, назви
  `1.x.0-snapshot.N`; звичайним гравцям і Docker без явної версії не пропонуються).
- Окремий репозиторій-експеримент; якщо дожене основний — можна зробити його основою.

## Плюси й мінуси такого порядку

**Плюси:** усе своє (мова, компілятор, JVM, графіка); мова виростає на справжній великій
задачі, а не на прикладах; NyxOS отримує мову, на якій реально писати систему (заміна C в ядрі).

**Мінуси:** до першої роботи JVM — ~5 місяців чисто мовної роботи; кожна помилка компілятора
стає помилкою JVM (лікується порівняльними тестами з C на кожному етапі); статичний режим «як C»
— фактично друга мова всередині NyxilumLang, її треба тримати узгодженою з динамічною.
